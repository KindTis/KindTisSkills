# 명세 티켓 등록

**Superpowers 상세 명세 → 간결한 Jira 본문 → 실제 명세 첨부**를 완성한다. 제품 구현과 실행·상태 관리는 이 스킬의 범위에 포함하지 않는다.

`Specification`이 지정한 첨부 `.md`가 상세 요구사항의 Source of Truth다. 본문과 충돌하면 해당 명세를 우선하며, 사용자의 새 변경 요청은 명세부터 반영한다.

## 대상과 명세 준비

현재 Jira 도구에서 대상 프로젝트·티켓, 허용 이슈 유형, 라벨, 부모 관계와 파일 첨부 기능을 확인한다. 호출은 실제 스키마를 따르며 경로·버전·도구명을 고정하지 않는다. 대상을 유일하게 정할 수 없을 때만 확인한다. 첨부 기능을 사용할 수 없으면 새 티켓부터 만들지 않는다.

요구의 목적, 기대 결과, 포함·제외 범위와 제약에 필요한 코드·문서를 조사한다. 핵심 미확정 사항은 확인하고 조사 한계는 명세에 남긴다.

기존 티켓은 본문·첨부·유형·라벨을 읽는다. `Specification`이 지정한 명세를 우선하며, 참조가 없으면 현재 명세를 유일하게 식별할 수 있을 때만 사용한다. 명세와 참조가 모두 없으면 기존 본문을 출발점으로 삼는다. 지정 파일이 없거나 후보가 여러 개면 확인한다. 본문에만 있는 상세 요구는 새 명세로 옮겨 보존한다.

현재 스킬 목록에서 **`superpowers:brainstorming`**을 찾아 실제 지침에 따라 명세를 작성·검토한다. 사용할 수 없으면 누락된 의존성을 보고하며 자체 명세 포맷으로 대체하지 않는다. 이 요청에서는 상세 Markdown 명세 작성까지 수행한다. 명세 작성 절차의 구현·커밋 단계가 승인 범위를 넘으면 수행하지 않는다.

- 이미 Superpowers로 완성된 명세는 현재 요구와 일치하면 재사용한다.
- 명세에는 상세 요구·설계·범위·제약·예외 처리·완료 조건·검증 기준을 담는다. 확인된 사실과 가정, 실제 검증 결과와 미실행 항목을 구분한다. 별도 고정 목차는 만들지 않는다.
- 한국어, UTF-8(BOM 없음)로 저장한다. 위치는 사용자 지정, 프로젝트 문서 규칙, 명세 스킬 기본 위치 순으로 선택하며, 없으면 현재 작업공간에 정해 알린다.
- 가능하면 `<JIRA-KEY>_<topic>_spec.md`로 저장한다. 신규 티켓은 임시 이름을 쓰고 실제 Key를 받은 뒤 정리한다. 기존 첨부를 보존하고 새 버전은 파일명으로 구분한다.

## Jira 본문

완성된 명세에서 다음 세 영역만 추출한다.

```markdown
## Overview

작업의 목적과 기대 결과를 2~5문장으로 설명한다.

## Spec Summary

- 명세에서 확정된 핵심 요구사항
- 주요 변경 범위
- 중요한 제약 또는 설계 결정
- 핵심 검증 결과

## Specification

Attachment: `<실제 첨부 파일명>.md`
```

`Spec Summary`는 첨부를 열지 않아도 작업의 핵심 방향을 이해할 수 있는 수준으로 작성한다. 검증 결과는 실제 확인한 경우에만 넣고, 판단에 영향을 주는 중요한 미검증 사항을 밝힌다. 에픽의 확정 실행 순서는 이 영역에 간결히 기록할 수 있다.

클래스·함수별 설계, 수정 파일 목록, 내부 자료구조, 상세 테스트·예외 처리, 긴 Acceptance Criteria·DoR·DoD·TODO는 첨부 명세에 둔다. Agent 로그, Codex 세션 정보, 서브에이전트 목록은 본문과 명세에 넣지 않는다.

## 이슈 유형과 라벨

완성된 명세를 기준으로 **유형과 대표 분류 라벨을 독립적으로** 선정한다.

- `Bug`: 기존 요구·명세·합의된 기대 동작을 충족하지 못하는 결함 해결.
- `Task`: 기능 추가, 의도된 요구 변경, 유지보수 등 일반 작업.

기존 기능을 수정한다는 이유만으로 Bug로 정하지 않는다. 결함과 변경 요구의 구분이 불명확하면 확인한다. 개별 작업은 Bug/Task, 에픽은 실제 지원되는 Epic 유형을 사용한다. 필요한 유형이나 계층을 지원하지 않으면 다른 유형으로 대체하지 않고 제약을 알린다.

| 라벨 | 주목적 |
| --- | --- |
| `feature-add` | 새로운 기능·동작 추가 |
| `feature-change` | 기존 기능의 동작 수정·변경·개선 |
| `refactor` | 외부 동작을 유지하는 내부 구조 개선 |
| `docs` | 문서 작성·수정 |
| `resource` | 이미지·음원·모델·콘텐츠 등 생성·수정 |
| `config` | 개발·빌드·배포·도구 환경 설정 |
| `other` | 위 분류에 해당하지 않는 작업 |

주목적과 핵심 산출물에 맞는 라벨 하나를 고른다. Bug에 feature-change를 자동 부여하지 않으며, 의도된 기능 변경인 Task에도 feature-change를 사용할 수 있다. 티켓용 명세를 작성한다는 이유로 docs를 선택하지 않는다. 새 분류나 세부 기능 라벨을 만들지 않으며, 정보 부족을 other로 처리하지 않는다.

기존 분류가 없으면 추가하고, 일치하면 재사용한다. 기존 분류가 충돌하거나 여러 개면 교체·삭제 전에 확인한다. 다른 라벨은 보존하며, 명세 보강만으로 기존 이슈 유형을 바꾸지 않는다.

## 등록과 확인

- **신규:** 명세에서 추출한 제목·본문과 선정한 유형·라벨로 생성한다. `Specification`은 일시적으로 `Attachment: 첨부 대기`로 두고, 실제 Key로 파일명을 정리해 첨부한다.
- **기존:** 새 명세를 먼저 첨부·검증한 후 요약과 `Specification`을 함께 갱신한다. 그전까지 기존 본문과 명세 참조를 유지한다. 본문의 중요한 정보·미디어를 보존하고 상태·담당자·우선순위 등 요청받지 않은 필드는 유지한다.

다음 결과를 확인한 뒤 등록 완료로 보고한다.

1. 파일이 대상 티켓에 실제 연결되어 있고, 첨부 내용이 로컬 원본과 일치한다. 로컬 경로·문서 링크·업로드 준비 응답은 첨부를 대신하지 않는다. 내려받아 확인할 때 원본을 덮어쓰지 않는다.
2. 저장된 본문은 명세와 일치하며 `Specification`은 검증한 실제 첨부 파일명을 가리킨다.
3. 재조회한 유형·라벨과 지정된 부모 소속이 확정한 내용과 일치한다. 부모 관계는 일반 링크로 대체하지 않는다.

부분 실패는 생성된 Key와 성공한 결과를 재사용하여 남은 단계만 복구한다. 쓰기 결과가 불명확하면 재조회하고, 그래도 확인할 수 없으면 추가 쓰기를 보류한다. 첨부 실패로 티켓을 재생성하거나 동일 파일을 중복 첨부하지 않는다. 이전 첨부·참조는 새 첨부 검증 전까지 보존하며, 이전 첨부를 자동 삭제하지 않는다.

결과에는 Jira Key·링크, 유형·라벨, 로컬 명세 경로와 실제 첨부 파일명, 반영 확인 결과를 간결히 담는다. 첨부 존재와 내용 일치 검증을 구분하고 실패·미확인 사항은 명시한다.

## 다른 절차에서 재사용

`jira:epic`이나 `jira:specify`가 전달한 기존 Key·범위·유형·부모 Key·선행 조건·준비된 명세에도 같은 규칙을 적용한다. 명세 준비만 요청된 단계에서는 파일과 미확정 사항을 반환하고, 등록 단계에서 생성·갱신·첨부를 이어간다. 일괄 보강에서 필요한 질문은 대상 Key와 함께 호출한 절차에 전달해 취합한다. 작업 분해·관계 연결은 에픽 스킬이, 일괄 대상 관리·상태 전환은 specify 스킬이 담당한다.
