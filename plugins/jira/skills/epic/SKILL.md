# 에픽 구성과 작업 실행 조정

공통 목표를 가진 큰 작업을 작은 실행 단위로 나누고 단위별 명세·이슈와 관계·순서를 구성한다. 완성 명세의 신규 발급은 `jira:spec-ticket`, 각 단일 이슈의 구현·검증은 `jira:work`를 사용한다. 실행까지 요청받았으면 작업별 배정·의존성·인계·전체 결과를 조정한다.

분해·명세 준비만 요청받았으면 등록하지 않고, 등록만 요청받았으면 작업 세션을 시작하지 않는다. 기존 에픽의 실행 요청은 현재 명세·하위 이슈·관계·순서를 검증하는 **작업 배정과 실행**에서 시작한다. 재분해·재등록을 강제하지 않으며 필요한 보완이 승인 범위를 넘으면 그 쟁점만 확인한다.

## 대상 확인

사용자가 지정한 요구·백로그 전체와 필요한 프로젝트 컨텍스트를 읽는다. 참고 자료의 과거 프로젝트·경로·실행 지시는 현재 요청의 대상으로 간주하지 않는다.

현재 Jira 기능으로 프로젝트, 기존 에픽 여부, 지원 이슈 유형·계층, 선행 관계의 종류·방향을 확인한다. 여기서 하위 작업은 에픽 아래의 개발 작업이며 `Sub-task` 유형을 뜻하지 않는다. 실제 부모 관계와 의존 관계를 구분한다.

생성 후 실제 초기 상태를 확인한다. 상태 반영은 이번 실행에 선택된 `jira:status`를 따른다. 필요한 유형·계층이 지원되지 않으면 제약을 반환하고 다른 유형이나 워크플로 변경으로 해결하지 않는다.

## 작업 분해

각 작업의 **완료 후 확인할 결과, 포함·제외 범위, 선행 조건, 대표 검증 흐름, 원문 근거**를 정리한다.

- 함께 있어야 동작하는 요소를 하나의 기능 흐름으로 묶는다. 클래스·화면·서버 등 기술 계층이나 예상 코드량으로 기계적으로 나누지 않는다.
- 선행 조건이 갖춰지면 사용자나 운영자가 결과를 확인할 수 있어야 한다. 앞 작업에 기능을 더하는 단위로 구성하되, 여러 독립 목표가 섞이면 나눈다.
- 원문 범위의 누락·중복·불필요한 추가를 확인한다. 제외 범위에는 근거를 남기고 공유 기반과 연결 검증의 담당 작업도 정한다.
- 권장 실행 순서와 반드시 충족해야 하는 선행 의존성을 구분한다. 순환 의존성이 있으면 작업 경계를 조정한다.

제목은 완성되는 기능을 표현한다. 분해 결과와 순서를 간결히 제시하고 기존 지시로 확정할 수 없는 범위·우선순위만 확인한다. 여러 에픽이 필요하면 범위를 확인한다.

## 명세 준비

현재 목록에서 `superpowers:brainstorming`을 찾아 요구 구체화와 에픽·작업 명세의 작성·검토까지만 적용한다. 의존성을 사용할 수 없으면 누락을 반환하며 자체 형식으로 대체하지 않는다. 명세 승인을 받은 뒤 승인된 Jira 발급·반영 단계로 이어가며 구현 계획 단계로 자동 진행하지 않는다. 명세 준비 승인만으로 구현·커밋을 시작하지 않는다.

- 에픽 명세: 전체 목표·범위, 공통 제약, 작업 경계·순서·의존성, 전체 완료·검증 기준.
- 작업 명세: 해당 티켓과 첨부만으로 이해할 수 있는 요구, 필요한 공통 제약과 선행 결과, 완료·검증 기준. 중요한 조건을 에픽 링크에만 남기지 않는다.

기존 완성 명세는 재사용하고 전체 범위·관계의 일치를 확인한다. 요구나 확인된 프로젝트 계약에 없는 클래스·함수 설계를 미리 고정하지 않는다. 접근 선택·명세 승인과 진행을 막는 미확정 사항을 취합해 확인한다. 명세 준비만 요청한 경우 파일·분해·순서·미확정 사항을 반환하고 종료한다.

## 등록과 실행 순서 연결

등록이 승인되고 명세가 확정되면 [공통 등록 규칙](../../references/spec-registration.md)을 읽는다. 본문·첨부·유형·대표 라벨·보존·검증은 이 규칙을 사용한다.

1. 신규 에픽은 완성 명세로 `jira:spec-ticket`을 통해 발급한다. 지정된 기존 에픽은 이 절차가 공통 규칙의 **기존 이슈 반영**을 수행한다. 실제 Key와 본문·첨부가 확인되면 하위 등록을 진행한다.
2. 작업별 완성 명세·유형·실제 부모 Key를 `spec-ticket`에 전달해 신규 하위 이슈를 발급한다.
3. 실제 부모 소속을 확인하고 필수 선행 의존성만 지원되는 관계와 올바른 방향으로 연결한다. 관계 조작은 이 절차가 담당한다.
4. 명세의 임시 작업 참조를 실제 Key로 정리한다. 바뀐 명세·본문은 공통 규칙의 **기존 이슈 반영과 실제 Key 참조 갱신**으로 처리한다. 기존 하위의 재개도 새로 발급하지 않고 필요한 기존 반영만 수행한다.

**에픽 본문의 `Spec Summary`에 확정 실행 순서를 실제 하위 Key로 기록한다.** 예: `실행 순서: <KEY-A> → <KEY-B> → <KEY-C>`. 승인된 병렬 묶음과 선후 관계를 명확히 적는다. 명세의 순서와 일치시켜 작업 배정 시 본문으로 순서를 확인할 수 있게 한다. 상세 분해표·테스트 시나리오는 첨부에 둔다.

## 구성 검증과 부분 실패

신규 발급의 명세·본문·첨부 검증은 `spec-ticket`의 결과를 재사용하고 기존 반영은 공통 규칙으로 확인한다. 에픽·하위 집합, 부모 관계, 선행 방향, 본문 실행 순서와 실제 초기 상태를 확인한다. 개별 이슈의 발급·첨부 검증만으로 전체 구성이 완료된 것으로 판단하지 않는다. 실제 Key 참조·부모 관계·필수 의존성·실행 순서까지 일치해야 전체 구성이 준비된 것이다.

부분 실패는 기존 Key와 성공 결과를 보존하고 남은 단계만 복구한다. 불명확한 쓰기는 재조회하며 생성 여부를 알 수 없으면 중복 생성하지 않는다. 에픽 등록·첨부 실패 시 하위 등록을 보류하고 특정 작업 실패 시 그 결과에 의존하는 단계만 보류한다. 관계 기능이 없으면 본문 링크로 대체 완료하지 않고 남은 관계를 보고한다.

등록까지만 요청받았으면 에픽·하위 Key와 링크, 작업별 결과·첨부 파일명, 실행 순서·필수 선행 관계와 실패·미확인 항목을 반환하고 종료한다. 실행도 요청받았으면 검증된 구성으로 아래 작업을 배정한다.

## 작업 배정과 실행

현재 에픽 본문·기준 명세, 실제 부모·자식 관계로 조회한 하위 목록과 각 기준 명세를 확인한다. **Description의 실행 순서**를 실제 하위 Key·선행 관계와 대조한다. 순서 누락·충돌은 기존 대화로 확정할 수 없으면 확인하며 이슈 번호나 생성일로 추측하지 않는다. 기존에 검증된 명세·등록·관계 결과는 재사용한다.

기본은 본문 순서에 따른 순차 실행이다. 명시된 병렬 그룹만 실제 의존성과 작업 공간이 분리되어 있을 때 병렬 실행한다. 조정 작업 에이전트는 실행 순서·의존성·세션 조정·코드 인계·결과 취합과 전체 완료 판단을 담당한다. 개발용 의존 지침은 미리 읽지 않고 해당 작업에 필요한 입력을 배정한다.

### 최소 배정 입력과 동일 업무 목표

각 이슈에 다음 입력만 준비한다.

- 단일 이슈 Key·URL과 해당 이슈를 `jira:work`로 구현·검증하는 업무 목표·완료 조건.
- 확인한 저장소와 사용자가 지정한 작업 공간. 지정이 없으면 현재 브랜치 사용 조건.
- 이슈의 `Specification`이 지정한 실제 기준 첨부 파일명·접근 경로.
- 필요한 선행 코드 기준과 재현 가능한 결과 참조·검증 근거.
- 해당 작업의 승인 범위·사용자 제약과 그 작업에 선택된 독립 지침.

자식의 업무 지침은 `jira:work`다. 그 이슈에 적용하도록 선택된 독립 지침만 함께 전달하고(이번 실행에 `jira:status`가 선택됐으면 포함해 각 세션이 자기 이슈의 상태·댓글을 반영하게 한다), 부모가 읽은 전체 스킬 목록을 복제하거나 선택되지 않은 지침을 임의 추가하지 않는다. 실제 goal 실행 지시도 입력에 포함하며 **'해당 이슈의 지정 명세를 `jira:work`로 구현·검증하고 완료 조건을 충족한다'**는 동일 업무 목표를 사용한다. 이슈 Key·범위·제약을 채운 목표를 준비하고 실제 세션의 goal objective와 일치하는지 확인한다.

### 독립 세션 실행과 확인

- **하위 이슈마다 별개의 최상위 세션**을 사용한다. child/subagent·기존 대화의 fork·현재 세션의 일괄 구현으로 대체하지 않는다. 각 독립 작업 에이전트가 자기 이슈의 주 에이전트로서 선택된 업무 지침을 수행한다. 각 주 에이전트는 자식을 직접 생성·호출하며 역할과 Advisor 호출 조건은 `improve:implement` 지침을 따른다.
- 현재 도구의 독립 세션 생성·goal·실행·결과 조회 기능을 확인한다. 네이티브 기능이 없을 때만 [독립 세션 연결](references/independent-sessions.md)을 사용한다. 기능이 없으면 준비한 입력과 제약을 알린다.
- 준비한 배정 입력과 동일 업무 목표를 첫 사용자 입력으로 전달한다. 생성된 세션의 독립성, 실제 goal objective·활성 상태와 실행 시작을 각각 확인하고 이슈 Key와 세션 ID의 대응을 보존한다. 세션 생성·입력 전송만으로 실제 실행을 판단하지 않는다.
- 생성·전송 응답이 불명확하면 기존 세션·goal·실행 상태를 조회해 같은 실행을 복구한다. 본문 순서에 맞춰 준비된 작업만 시작하고 세션의 실제 결과·검증 근거·코드 인계를 확인하며 다음 작업으로 이어간다.
- 작업 세션이 판단·승인 요청으로 멈추면 조정 에이전트가 근거로 정할 수 있는 것은 판단하고, 사용자 판단이 필요한 것만 모아 묻는다. 답은 같은 세션에 후속 입력으로 전달하며 새 세션을 만들지 않는다.

### 선행 코드와 실패 복구

후속 작업은 필수 선행 코드가 실제 준비된 기준에서 시작해야 한다. 원본을 보존한 재현 가능한 스냅샷·패치와 검증 근거를 전달한다. Jira·goal 상태만으로 코드 전달을 대신하지 않는다. 앞 작업의 구현·필수 검증·코드 인계가 끝났다면 별도로 남은 사용자 인수·릴리스 승인은 실제 구현 의존성이 없는 한 후속 작업을 막지 않는다.

작업 간 영향·범위 변경·스스로 해결할 수 없는 장애는 각 작업 에이전트의 근거를 받아 조정한다. 같은 승인 범위의 재작업마다 재승인을 요구하지 않는다. 의존성의 설계 문제·중요한 구조 영향을 근거로 해결하지 못하면 Advisor에게 자문한다. 실패하면 의존하는 후속 작업만 보류하고 다른 작업도 본문의 순서·병렬 허용 범위를 따른다.

기존 Key·세션·실제 실행·성공한 결과를 재사용한다. 오류나 연결 종료만으로 중복 세션·실행을 만들지 않는다. 진행 추적은 도구의 대기 기능과 변경분을 우선하며 새 상태·증거·판단 필요가 없으면 같은 조회·재지시·기록 갱신을 반복하지 않는다. 필요한 의존성 판단·장애 복구·최종 증거 확인은 수행한다.

## 전체 결과와 완료 판단

각 독립 작업 에이전트는 자기 이슈의 구현·리뷰·검증과 완료 판단을 담당하고, 조정 작업 에이전트는 필수 하위 결과와 전체 완료 조건의 증거로 에픽의 최종 완료를 판단한다. 자식 goal 완료만으로 에픽 완료를 결정하지 않는다. 추가 연결 검증이 필요하면 승인 범위와 지정 담당 작업에서 수행한다.

goal 완료·개발 완료와 남은 사용자 인수·Jira 완료를 구분한다. 하위 Key별 세션·goal 결과, 개발·검증 근거와 남은 항목, 실행 순서·선행 코드 전달 결과, 작업 공간·코드 결과 참조와 보고서 링크를 반환한다. 시작만 확인했다면 시작 사실까지만 보고한다. 적용되는 전역 goal 완료 보고 절차를 따르며 보고서 배포 실패는 개발 완료와 구분한다.
