# Jira 상태와 댓글 보고

작업 에이전트가 확정한 단계와 결과를 Jira에 반영한다. 명세 해석·구현·검증 방법과 완료 여부의 판단은 담당하지 않는다. 단순 티켓 조회나 사전 내용 검토는 착수 신호가 아니며, 주기적인 중간 보고는 작성하지 않는다.

## 입력과 대상

대상 Key/URL, 명세 준비·개발의 구분, 실제 단계, 작업 범위와 결과를 사용한다. 확인 요청에는 진행 불가 사유·필요한 답변이나 조치·재개 조건이 필요하다. 에픽은 이번 갱신 대상 하위 Key와 전체 단계의 확정 여부도 받는다. 기존 대화에서 확인되지 않은 필수 입력만 확인한다.

현재 Jira 도구의 실제 스키마로 유형·상태·가능한 전환·기존 댓글을 조회한다. 에픽은 실제 부모·자식 관계와 필요한 하위 현황을 확인한다. 불완전한 목록으로 전체 완료를 판단하지 않는다. 사이트·대상이 모호할 때만 확인하고, 도구명이나 상태 ID를 고정하지 않는다.

변경 범위는 지정된 티켓의 상태와 보고 댓글이다. Description·명세·분류·담당자 등 다른 필드, 워크플로 설정, 별도 실행 기록·잠금·타이머는 변경하거나 만들지 않는다.

## 상태 대응

| 전달받은 실제 단계 | 목표 상태 | 댓글 |
| --- | --- | --- |
| 명세 준비 중·미확정이며 진행을 막는 확인 요청이 없음 | `명세 필요` 유지 | 없음 |
| 명세 확정·첨부·본문 반영 완료, 개발 미착수 | `할 일` | 없음 |
| 실제 개발 착수 | `진행 중` | 착수 보고 |
| 답변·사전 승인·문제 해결이 필요해 작업을 계속할 수 없음 | `확인 요청` | 확인 요청 |
| 확인 요청 해소 | 실제 단계에 맞는 상태로 복귀 | 처음 개발에 착수할 때만 착수 보고 |
| 구현과 필요한 테스트를 마친 결과물의 리뷰·필수 승인 대기 | `검토 중` | 없음 |
| 구현 후 리뷰에 따른 수정 재개 | `진행 중` | 같은 작업의 착수 보고 반복 없음 |
| 필요한 검증·리뷰를 포함한 개발 완료 확정 | `완료` | 완료 보고 |

- **명세 필요·할 일:** 둘 다 상태 범주는 `할 일(To Do)`이다. 명세 준비 중에는 `명세 필요`, 준비가 완료된 개발 대기는 `할 일`로 반영한다. 준비 완료 판단은 호출자가 전달하며 이 스킬이 명세를 검사하지 않는다. 명세 보강만으로 개발 착수·완료 보고를 남기지 않는다.
- **확인 요청:** 사용자 판단, 권한, 외부 장애, 필수 선행 작업 등으로 해당 티켓을 계속할 수 없을 때 적용한다. 독립적인 작업을 계속할 수 있으면 실제 작업 상태를 유지한다. 재개 조건이 충족되어야 해소하며, 다른 차단 사유가 남으면 유지한다. 상태 범주는 `진행 중`이지만 착수 사실을 뜻하지 않는다. 개발 미착수 요청 해소 시 명세 준비가 남으면 `명세 필요`, 준비가 끝났으면 `할 일`로 복귀한다. 프로젝트 범주가 다르면 차이를 보고한다.
- **검토 중:** 구현 후 결과물 리뷰만 해당한다. 요구·명세·설계의 사전 검토에는 쓰지 않는다. '검토 중'·'승인 대기'만 전달되어 단계를 구분할 수 없으면 상태 변경 전에 확인한다.

현재 상태가 목표와 같으면 유지한다. 다르면 가능한 전환의 **도착 상태**를 확인해 전환한다. 프로젝트의 다른 상태명은 확인된 의미 대응을 사용하며, 대응이나 전환이 없으면 제약을 보고한다. 명시적인 재작업 판단 없이 완료 티켓을 다시 열거나, 과거 단계를 기록하려고 상태를 차례로 재연하지 않는다.

## 보고 댓글

보고는 각 대상 티켓의 Jira 댓글에 한국어로 남긴다. 첫 줄은 다음 접두사를 사용한다.

| 첫 줄 | 내용 |
| --- | --- |
| `[Agent] 착수 보고` | 실제 착수한 범위. 에픽은 전체 작업 대상과 지금 착수한 하위 Key를 구분 |
| `[Agent] 확인 요청` | 멈춘 이유, 필요한 답변·조치, 재개 조건과 확인된 해결 주체. 에픽은 관련 하위 Key 포함 |
| `[Agent] 완료 보고` | 확정된 개발 완료 범위·결과, 전달받은 검증 근거·링크와 중요한 제한. 에픽은 전체 결과와 관련 하위 결과 요약 |

공통으로 실제 Jira 상태를 적고, 전환이 실패했다면 작업 사실과 상태 미반영을 구분한다. 받은 검증 근거가 없으면 누락을 밝힌다. 원시 로그·세션 정보·에이전트 목록·임의 완료율은 넣지 않는다.

재개·재시도에서는 같은 작업의 기존 보고를 재사용한다. `[Agent]`가 없는 기존 보고도 내용과 범위가 같으면 인정하며, 접두사 보정을 위한 재작성은 하지 않는다. 같은 확인 요청은 필요한 조치가 바뀌거나 해소 후 다시 막힌 경우에만 새로 기록한다. 별도 해소 댓글은 요구하지 않는다. 완료 후 새로 승인된 재작업은 구분하고, 다른 사람의 댓글은 수정·삭제하지 않는다.

## 에픽 처리

에픽 전체 범위와 이번 갱신 범위를 구분한다. 지정된 대상만 갱신하며, 별도 세션이 반영한 상태·댓글은 재사용한다. 아직 작업하지 않는 하위 티켓을 일괄 전환하지 않는다. 명세 보강은 위의 명세 준비 상태를 티켓별로 반영하며 개발 착수로 집계하지 않는다. 아래 표는 개발 단계에 적용한다.

| 상황 | 에픽 반영 |
| --- | --- |
| 첫 하위 작업의 실제 착수 | `진행 중`과 착수 보고 |
| 일부 하위만 차단·리뷰·수정·완료 | 전체 단계에 변화가 없으면 유지. 해당 하위만 자신의 단계 반영 |
| 전체 진행 불가 또는 그 해소 | 전체 진행 가능 여부에 따라 `확인 요청` 또는 실제 단계로 복귀 |
| 전체 구현 결과물 리뷰 확정 | 최신 하위 현황과 모순이 없으면 `검토 중` |
| 전체 수정 재개 확정 | `진행 중` |
| 전체 완료 확정 | 필수 하위 완료와 전체 완료 근거 확인 후 `완료`와 완료 보고 |

전체를 올리기 전에는 필요한 하위 목록·최신 상태를 확인한다. 미착수·수정 중인 필수 작업이 남으면 전체 리뷰로, 필수 작업이 미완료이면 전체 완료로 올리지 않는다. 제외된 작업은 승인되거나 확정된 범위 근거가 있어야 한다. 모든 하위가 완료되어도 전체 완료 판단을 대신하지 않는다.

하나의 하위가 막혔다고 전체를 확인 요청으로 바꾸지 않는다. 일부 요청 해소로 전체 진행이 가능해지면 에픽은 실제 단계로 복귀하고, 아직 막힌 하위는 유지할 수 있다. 일부 작업만 맡은 요청이 끝나도 에픽은 남은 전체 작업을 나타낸다.

## 반영 확인과 실패

상태 전환과 댓글 저장은 별도로 확인한다. 응답이 실제 저장 결과를 제공하면 사용하고, 불명확하면 재조회한다. 댓글 내용과 `[Agent]` 접두사도 확인한다. 한쪽만 성공했으면 누락된 쪽만 복구한다.

쓰기 결과를 재조회해도 알 수 없으면 중복 쓰기를 보류한다. 권한·전환·저장 실패는 실제 상태와 함께 보고하며, 성공한 하위 갱신을 되돌리지 않는다. 영향받지 않는 갱신은 계속하고 같은 원인의 실패를 반복하지 않는다.

티켓별 Key·링크, 실제 상태, 보고 존재·저장 결과, 실패·미확인 사항을 반환한다. 이 스킬의 완료는 상태·보고 반영의 완료이며 개발 완료를 뜻하지 않는다.
