# 기존 아이디어 이슈 명세화

기존 Key를 유지하며 **대상 선정 → 현재 명세 식별·재사용 → 요구 구체화·명세 승인 → 기존 이슈 반영·검증**을 수행한다. 신규 발급이나 제품 구현은 하지 않는다. 상세 명세 작성·첨부·본문 갱신을 이 절차가 담당한다.

## 대상 선정

단일 Key/URL, 지정 목록·보드·프로젝트·조회 조건과 프로젝트 지침으로 범위를 정한다. 현재 Jira 도구의 실제 스키마를 사용하며 유일하게 정할 수 없는 대상만 확인한다.

- 목록·프로젝트 일괄 처리의 기본 대상은 실제 `명세 필요` 상태다. 열 이름이나 첨부 유무만으로 판단하지 않는다. 필요한 조회 페이지를 모두 확인하고 Key 중복을 제거한다.
- 에픽 하위는 실제 부모·자식 관계로 조회하며 에픽 자체는 명시된 대상일 때만 포함한다. 작업 분해·새 이슈 생성은 하지 않는다.
- 명세 보강의 이어가기임이 명시적 재개 요청이나 기존 대화·댓글로 확인되는 `확인 요청` 이슈는 포함한다. 개발 차단과 구분한다.
- 다른 상태는 일괄 기본 대상에서 제외한다. 단일 지정이나 명시적으로 승인된 다른 상태의 보강은 처리할 수 있지만 개발 진행·완료 상태를 되돌리지 않는다.

티켓별 본문·첨부·현재 상태와 필요한 컨텍스트를 읽고 공통 자료를 재사용한다. 대상이 없으면 결과를 알리고 종료한다.

## 현재 명세와 요구 구체화

[공통 등록 규칙](../../references/spec-registration.md)을 읽는다. `Specification`이 지정한 명세를 우선하며 참조가 없으면 현재 명세를 유일하게 식별할 수 있을 때만 사용한다. 지정 파일 누락·동명 중복·여러 후보는 확인한다. 본문과 명세가 모두 없으면 원래 아이디어에서 출발하고, 본문에만 남은 상세 요구는 보존해 명세에 반영한다.

현재 목록에서 `superpowers:brainstorming`을 찾아 요구 구체화와 명세 작성·검토까지만 적용한다. 사용할 수 없으면 누락 의존성을 반환하며 별도 자체 형식으로 대체하지 않는다. 명세 승인 후에는 승인된 기존 Jira 반영 단계로 이어가며 구현 계획 단계로 자동 진행하지 않는다. 구현·커밋은 명세 보강 승인에 포함되지 않는다. 현재 요구에 맞는 완성 명세는 재사용하고 첨부가 있는데 참조만 누락된 경우에는 필요한 복구만 한다.

명세에는 상세 요구·설계·포함·제외 범위·제약·예외·완료 조건·검증 기준을 담으며 별도 고정 목차를 만들지 않는다. 확인된 사실·가정, 실제 검증·미실행을 구분한다. 한국어 UTF-8(BOM 없음)로 저장하고 위치는 사용자 지정, 프로젝트 규칙, 명세 스킬 기본 위치 순으로 따른다.

공통 질문을 묶고 개별 질문에는 Key를 붙인다. 접근 선택·명세 승인도 같은 방식으로 취합해 확인한다. 원래 요구와 새 제안을 구분하고 핵심 미확정 사항을 임의 확정하지 않는다. 답변이 필요한 이슈만 보류하고 공유 결정에 의존하는 이슈는 함께 보류한다. 독립적인 승인 작업은 계속한다.

## 기존 이슈 반영과 검증

필요한 결정·명세 승인이 확정되면 공통 규칙의 **기존 이슈 반영**과 **저장 검증·부분 실패**를 수행한다. 명세 준비만 승인된 요청은 파일·검토 결과까지만 반환하고 Jira 첨부·본문을 변경하지 않는다.

파일 생성만으로 준비 완료라 하지 않으며 필요한 결정·승인과 첨부·본문·분류 검증을 모두 확인한다.

기존 이슈 갱신 직전에 상태·대상 조건을 다시 확인한다. 기본 일괄 처리 중 다른 작업으로 개발이 시작되었거나 완료됐으면 추가 갱신 없이 제외 사실을 반환한다. 해당 상태의 보강이 명시적으로 승인됐으면 기존 개발 상태·요청받지 않은 필드를 보존해 명세만 반영한다.

## 이어가기와 결과

성공한 명세·첨부·본문과 검증 결과를 재사용하고 남은 단계만 복구한다. 불명확한 쓰기는 공통 규칙에 따라 확인한다.

결과는 **명세 반영 완료, 확인 필요, 실패·미확인, 제외**로 묶어 Key·링크와 이유를 반환한다. 실제 첨부 파일명·본문·분류 검증 결과와 남은 항목을 포함한다. 여기서 완료는 명세 작업의 완료이며 개발 완료를 뜻하지 않는다.
