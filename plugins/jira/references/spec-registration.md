# 명세·본문·첨부 등록 공통 규칙

`spec-ticket`의 신규 발급, `specify`의 기존 이슈 명세 반영, `epic`의 기존 에픽 반영·실제 Key 참조 갱신에 사용한다. 명세 작성과 작업 분해는 각 담당 절차가 수행한다.

## 기준 명세와 Jira 본문

Description의 `Specification`이 지정한 첨부 Markdown이 상세 요구의 기준이다. 본문과 충돌하면 그 명세를 우선하며 새 요구 변경은 담당 절차에서 명세부터 확정한다. 한국어 UTF-8(BOM 없음) 원본을 보존한다. 가능하면 `<JIRA-KEY>_<topic>_spec.md`를 사용하고, 신규 발급 전에는 임시 이름을 쓴다. 새 버전은 파일명으로 구분한다.

완성된 명세에서 다음 세 영역을 추출한다.

```markdown
## Overview

작업의 목적과 기대 결과를 2~5문장으로 설명한다.

## Spec Summary

- 명세에서 확정된 핵심 요구사항과 주요 범위
- 중요한 제약 또는 설계 결정
- 실제 확인한 핵심 검증 결과와 중요한 미검증 사항

## Specification

Attachment: `<실제 첨부 파일명>.md`
```

요약은 첨부를 열지 않아도 핵심 방향을 이해할 수 있게 작성한다. 에픽의 확정 실행 순서는 실제 하위 Key로 요약에 적을 수 있다. 클래스·함수 설계, 수정 파일 목록, 내부 구조, 상세 테스트·예외 처리, 긴 완료 조건·TODO는 첨부에 둔다. Agent 로그·Codex 세션 정보·서브에이전트 목록은 본문과 명세에 넣지 않는다.

## 유형·대표 라벨과 기존 필드

완성 명세를 기준으로 유형과 대표 라벨을 독립적으로 선정한다.

- `Bug`: 기존 요구·명세·합의된 기대 동작을 충족하지 못하는 결함 해결.
- `Task`: 기능 추가, 의도된 요구 변경, 유지보수 등 일반 작업.
- 에픽: 실제 지원되는 `Epic` 유형. 개별 작업은 Bug/Task를 사용한다.

기존 기능을 수정한다는 이유만으로 Bug를 선택하지 않는다. 구분이 불명확하면 확인한다. 필요한 유형·계층을 지원하지 않으면 다른 유형으로 대체하지 않고 제약을 반환한다.

| 대표 라벨 | 주목적 |
| --- | --- |
| `feature-add` | 새로운 기능·동작 추가 |
| `feature-change` | 기존 기능의 동작 수정·변경·개선 |
| `refactor` | 외부 동작을 유지하는 내부 구조 개선 |
| `docs` | 문서 작성·수정 |
| `resource` | 이미지·음원·모델·콘텐츠 등 생성·수정 |
| `config` | 개발·빌드·배포·도구 환경 설정 |
| `other` | 위 분류에 해당하지 않는 작업 |

주목적과 핵심 산출물에 맞는 하나를 고른다. Bug에 feature-change를 자동 부여하지 않으며 Task에도 feature-change를 사용할 수 있다. 티켓용 명세를 작성한다는 이유로 docs를 선택하지 않는다. 새 분류·세부 기능 라벨을 만들지 않으며 정보 부족을 other로 처리하지 않는다.

기존 대표 분류가 없으면 추가하고, 일치하면 재사용한다. 충돌하거나 여러 개면 교체·삭제 전에 확인한다. 다른 라벨을 보존하고, 명세 보강만으로 기존 유형을 바꾸지 않는다. 기존 본문의 중요한 정보·미디어와 상태·담당자·우선순위 등 요청받지 않은 필드를 보존한다.

## 신규 발급

현재 도구의 실제 스키마로 대상 프로젝트, 유형·계층·라벨·부모와 파일 첨부 기능을 확인한다. 첨부 기능이 없으면 먼저 티켓부터 만들지 않는다.

명세의 제목·본문과 확정한 유형·대표 라벨·부모로 생성한다. `Specification`은 일시적으로 `Attachment: 첨부 대기`로 두고 실제 Key를 받은 뒤 파일명을 정리해 첨부·검증하고 본문 참조를 갱신한다. 생성 결과와 실제 초기 상태를 확인한다.

## 기존 이슈 반영과 실제 Key 참조 갱신

기존 Key·본문·첨부·유형·라벨·부모를 재조회한다. 확정된 새 명세를 먼저 첨부·검증한 뒤 요약과 `Specification`을 함께 갱신한다. 새 첨부 검증 전까지 기존 본문·참조를 유지하며 이전 첨부를 자동 삭제하지 않는다. 내용이 동일하고 현재 첨부·참조가 검증됐다면 재사용하며 참조만 누락됐으면 필요한 본문 갱신만 수행한다.

에픽의 임시 작업 참조를 실제 Key로 바꿀 때도 이 기존 반영 순서를 따른다. 바뀐 명세·요약·실행 순서를 일치시키고 필요한 새 버전을 검증한 뒤 참조를 바꾼다.

## 저장 검증과 부분 실패

다음 결과를 확인해 반환한다.

1. 파일이 대상 티켓에 실제 연결되고 첨부 내용이 로컬 원본과 일치한다. 로컬 경로·문서 링크·업로드 준비 응답은 실제 첨부가 아니다. 내려받을 때 원본을 덮어쓰지 않는다.
2. 저장된 본문이 명세와 일치하고 `Specification`이 검증한 실제 파일명을 가리킨다.
3. 재조회한 유형·라벨·지정된 부모 소속이 확정 내용과 일치한다. 부모 관계는 일반 링크로 대체하지 않는다.

생성된 Key와 성공한 결과를 보존하고 남은 단계만 복구한다. 불명확한 쓰기는 재조회하며 확인할 수 없으면 해당 쓰기를 보류한다. 첨부 실패로 티켓을 재생성하거나 동일 파일을 중복 첨부하지 않는다. 같은 원인의 실패를 근거 변화 없이 반복하지 않는다.

Key·링크, 유형·라벨·부모, 로컬 명세 경로·실제 첨부 파일명, 첨부 존재와 내용 일치, 본문 반영의 확인 결과를 구분한다. 실패·미확인·남은 항목도 함께 전달한다.
