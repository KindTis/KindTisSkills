# 리뷰어 계약

주 에이전트가 리뷰어에게 보내는 내용이다. 모델·추론 수준은 역할 설정을, 위임 경계는 [위임 공통 계약](../../../references/delegation.md)을 따른다.

## 보내는 것

- **첫 회차:** 명세 경로와 이번 회차의 버전, 개선인지 검토만인지, 적용 규칙, 관련 저장소 위치, 아래 **리허설 방식**·**검증 사례 리뷰**와 맡은 축의 절. 사실 자료만 보낸다. 주 에이전트의 평가와 예상 지적은 답할 때 쓴다.
- **이후 회차:** 지적마다의 답(반영한 변경 또는 반영하지 않는 이유)과 명세 diff.
- **대조 회차:** 두 축의 산출물을 넣은 명세 diff. 대조 회차임을 밝혀 보낸다.

## 리허설 방식

명세를 읽고 평하지 않는다. 명세만 가지고 자기 축의 일을 실제로 해 본다. 해 보다가 더 나아갈 수 없는 곳과, 아래 검증 사례 리뷰에서 근거가 드러난 문제가 지적이다.

- **추측:** 명세가 정하지 않아, 추측해야 나아갈 수 있는 곳.
- **모순:** 명세의 두 곳이, 또는 명세와 기존 동작이 서로 다른 답을 주는 곳.
- **어긋남:** 명세대로 하면 명세가 밝힌 목표에 닿지 않거나, 만들거나 확인할 수 없는 곳.

뜻을 바꾸지 않는 표현 제안과 명세의 범위 밖 아이디어는 지적이 아니다.

명세가 정해야 하는 결정은 결정 트리를 이룬다. 결정마다 그 결정에 달린 결정이 가지로 붙는다. frontier는 전제가 이미 정해진 결정들이다. 회차마다 frontier 전체를 해 보고, 열린 결정에 달린 가지는 그 결정이 정해진 다음 회차에 해 본다. 사실은 저장소에서 직접 확인하고, 결정은 부모에게 올린다.

지적마다 막힌 곳, 정해야 할 결정, 추천 답과 근거, 명세에 넣을 문장(이전·이후)을 적는다.

이후 회차에는 먼저 자기 지적마다 부모의 답으로 닫혔는지 정한다. 닫히지 않았으면 근거와 함께 한 번 더 올린다. 정해진 결정은 새 근거가 있을 때만 다시 연다. 부모가 Advisor 자문으로 정했다고 답한 지적은 닫힌 것으로 다루고, 이견이 남으면 완료 보고에 한 줄로 남긴다. 그다음 diff가 닿은 가지를 다시 해 보고 새 frontier로 나아간다.

자기 축의 검증 사례 리뷰를 마쳤고 열린 지적이 없고 frontier가 비면, 곧 모든 가지를 해 봤고 말없이 가정한 것이 없으면 `REHEARSAL_COMPLETE`와 함께 자기 축의 산출물을 반환한다. 사용자 결정을 기다리는 가지는 그 사실과 함께 남긴다.

부모가 대조 회차라고 밝혀 보내면 diff에 들어온 상대 축의 산출물을 자기 리허설과 대조한다. 어긋나는 곳은 지적으로 올리고, 없으면 `REVIEW_COMPLETE`를 보고한다. 그 뒤 명세가 바뀌어 diff를 받으면 닿은 곳을 다시 해 보고 다시 보고한다.

검토만 요청된 회차에는 열린 결정에 추천 답을 가정하고 끝까지 해 본 뒤, 가정에 달린 지적을 표시해 반환한다. 완료 보고는 하지 않고, 사례와 제약은 초안으로 함께 반환한다.

## 검증 사례 리뷰

명세에 이미 적힌 검증 사례와 검증 요구도 자기 축의 리허설과 대조한다. 개별 사례와 사례 집합을 다음 기준으로 비판적으로 검토한다.

| 기준 | 확인할 것과 개선 방향 |
|---|---|
| 필요성 | 어떤 요구·결정·알려진 실패 위험을 확인하며, 빼면 무엇을 놓치는가? 연결 근거가 없는 사례는 삭제를 제안한다. |
| 충분성 | 사례가 모두 통과해도 중요한 요구를 어기는 구현이 가능한가? 결과를 가르는 분기·경계·실패 사례와 관측 가능한 판정 기준의 누락을 보완한다. |
| 중복 | 같은 상황·동작을 같은 판정으로 확인하는 다른 사례가 있는가? 서로 다른 요구의 구분과 판정 기준을 유지하며 의미가 같은 사례를 병합한다. |
| 과잉 | 요구와 알려진 위험에 비해 입력 조합·실행 시간·환경·검증 수단을 과도하게 강제하는가? 같은 판단을 할 수 있는 더 가벼운 범위로 조정을 제안한다. |

지적에는 연결된 요구·사례, 무엇을 놓치거나 겹치거나 불필요하게 확인하는지, 권장 변경(추가·수정·병합·삭제)과 근거를 적는다. 사례 수를 늘리거나 줄이는 것 자체를 목표로 삼지 않는다. 같은 코드 경로를 탈 것이라는 추측으로 서로 다른 동작 사례를 합치지 않으며, 실제 실행할 대표 사례와 수단은 구현 단계에서 고른다.

사용자가 명시한 검증은 삭제·축소하거나 다른 수단으로 대체하지 않는다. 과잉으로 판단되면 근거와 대안을 부모에게 올려 사용자 결정 대기로 남긴다.

## Planner: 수용 리허설

명세의 모든 사용자 흐름을 처음부터 끝까지, 실패와 예외 분기까지 따라간다. 단계마다 사용자가 무엇을 하고 무엇이 관측되는지 적어 본다. 사용자 목표·흐름·결과를 가르는 결정에 비추어 필요한 사례, 빠진 동작, 의미가 겹치는 사례를 찾는다.

- **산출물:** 사례. 어떤 상황에서 무엇을 하면 무엇이 관측되는지를 한 줄로 적는다. 결과를 가르는 결정마다 하나를 둔다.
- **대조:** 제약이 만들어 내는, 사용자에게 보이는 동작이 사례에 있는지 본다.
- **추가로 받는 것:** 소프트웨어인지 게임인지, 제품·디자인 규칙, 관련 사용자 흐름과 기존 동작.

## Programmer: 구축 리허설

**단계:** 명세 요구.

명세의 모든 요구를 실제 코드베이스에 놓아 본다. 요구마다 어디에 들어가는지, 기존 동작과 부딪히는지, 무엇으로 확인할 수 있는지를 저장소에서 확인한다. 사례의 판정 기준이 잘못된 구현을 걸러낼 수 있는지, 결과를 관측할 수 있는지, 검증 조건과 수단에 기술적 근거가 있는지 확인한다.

- **산출물:** 제약. 만드는 방식을 묶는 결정만 적는다. 인터페이스, 데이터 형식, 실패 동작, 기존 동작과 부딪히는 곳의 처리가 여기에 든다.
- **대조:** 사례마다 그 결과를 관측할 수단이 있는지, 같은 상황에 자기 리허설과 다른 결과를 적은 사례가 없는지 본다.
- **추가로 받는 것:** 플랫폼·아키텍처 규칙, 관련 소스·테스트·에셋·설정, 사용 가능한 빌드·검증 명령.
