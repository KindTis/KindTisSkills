# 진행 기록과 완료 보고 계약

## Progress record

프로젝트 루트 기준 `docs/reviewing-and-implementing-specs/yyyy-mm-dd-{작업명}.md`에 한국어 Markdown을 UTF-8(BOM 없음)으로 저장한다. 작업 시작의 로컬 날짜와 안전한 작업명을 사용하고 준비 단계에 절대 경로를 남긴다. 세션 재개·날짜 변경·worktree 이동 후에도 같은 기록을 이어 쓰며 기존 항목을 보존한다. 재개할 때 저장된 현재 상태와 미결 사항을 먼저 확인한다.

기록 작성 권한이 승인된 범위에 있을 때 주 에이전트가 Main 판단·필요한 설계 자문과 담당자 결과를 취합해 직접 작성·저장한다. 검토만 요청됐고 파일 작성이 승인되지 않았다면 새 파일을 만들지 말고 검토 결과를 응답으로 인계한다.

짧은 현재 상태 뒤에 주요 진행 기록과 최종 결과를 둔다. 모든 도구 호출 전후에 기록하거나 전체 응답·대화·원시 로그를 복사할 필요는 없다. 핵심 지적→판단→실제 수정→검증의 연결과 재현 가능한 증거를 작업 중 보존한다. 뒤늦게 복구한 기록은 출처와 복구 사실을 명시하며 당시 남긴 증거로 가장하지 않는다.

## Save checkpoints

| 단계 또는 사건 | 필요한 기록 |
|---|---|
| 준비·재개 | 승인 범위, 작업·기록 경로, 정본 명세·불변 snapshot, 관련 규칙, baseline·기존 사용자 변경, 개발 의존성/이후 수용 구분, 완료 기준, 현재 단계 |
| 독립 요구 리뷰 | 역할·가능한 agent/session ID·검토 snapshot, 핵심 지적·근거·영향 요구, 미결 질문과 결론. Planner/Programmer 최초 독립성을 확인 |
| Main 판단과 필요한 설계 자문 | 지적 ID와 `ACCEPT`/`REJECT`/`MAIN_DECISION`/`DEFER`/`EXTERNAL_AUTHORITY_REQUIRED`, 이유·영향 요구·중요 가정. 수정을 제안한 상태와 실제 반영을 구분 |
| 명세 반영 | 변경 요구·이전과 이후 규칙·실제 명세 파일, 정본 버전과 변경부 재검토 결과 |
| 검토·미결 | 검토 snapshot·산출물, 확인한 요구·남은 질문, 조정·변경부 재검토와 생략 이유 |
| 중단·인계·완료 | 현재 단계·완료 사항·실제로 막힌 개발 작업/근거·후속 절차, 개발 상태와 이후 사용자 수용·외부 승인·보고서 상태 |

역할별 검토 이력은 구분하고 지적에 안정적인 ID를 붙인다. 반복 또는 재개 지적은 새 지적 수로 부풀리지 않는다. 겹치는 지적은 관련 역할 attribution을 보존한다. 라운드·지적 수는 이해에 필요한 경우 저장된 기록에서 집계한다. 신규 지적 0건도 검토한 범위와 결론을 남기되 고정 숫자 표를 채우는 것을 완료 기준으로 삼지 않는다.

요청 모델·추론 수준을 기록한다. 런타임에서 실제 설정을 확인할 수 있으면 그 관측 증거를 함께 남긴다. 확인할 수 없으면 “요청 프로필, 실제 적용 관측 불가”로 구분하며 성공 응답만으로 모델이 적용됐다고 단정하지 않는다.

## Finding entry

각 중요한 지적에는 다음 내용이 필요하다. 간결한 문단이나 표로 작성해도 된다.

- **지적:** 식별자, 심각도 또는 단순화 분류, 관련 요구/명세 위치, 구체적인 문제와 중요성.
- **판단:** Main 결정과 증거, 필요한 경우 요청한 설계 자문. 미결이면 판단 대기, 채택했으나 수정 전이면 반영 대기.
- **실제 수정:** 이전·이후 동작이나 규칙, 변경 명세 파일·요구, 거절·유보한 경우 수정하지 않은 이유.
- **검증·재검토:** 실행 증거와 영향 범위, 독립 리뷰어의 해결 여부 또는 남은 문제.


## 명세 결과 인계

원본·최종 명세 경로와 버전, 채택·거절·유보한 지적과 이유, 실제 명세 변경, 변경부 독립 재검토와 남은 결정을 반환한다. 명세 개선 완료를 제품 구현·E2E 통과나 구현 goal 완료로 표시하지 않는다. 명세 문서는 Cloudflare 업로드 대상이 아니다.
