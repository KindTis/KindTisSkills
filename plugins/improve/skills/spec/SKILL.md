# 명세 작성·개선

명세만으로 사용자 동작·결과와 필요한 제약을 이해하고 구현·판정할 수 있게 한다. Planner가 문안을 작성하고 두 리뷰어가 수용·구축 관점에서 확인한다. 같은 최종 명세의 검토 범위를 확인하고 열린 유효 지적·판정 보류가 없어질 때까지 개선한다.

## 범위와 입력

작성·개선 요청은 문안 수정과 반복 검토를 포함한다. 검토만 요청은 요청된 검토 결과와 추천을 반환하며 파일 작성·Planner 집필을 추가하지 않는다. 사용자 목표·원문 제약, 대상 명세, 관련 저장소와 규칙, 기존 사용자 변경을 확인한다.

명세 개선 완료는 사용자 검토용 결과의 준비다. 사용자 승인이나 구현 지시를 대신하지 않으며 구현 계획·구현으로 자동 전환하지 않는다. 이미 승인된 같은 버전은 재승인받지 않는다.

준비 시 [위임 계약](../../references/delegation.md), [리뷰 계약](../../references/review-contract.md)을 읽고 역할에 필요한 계약을 전달한다. 작성·개선 기록은 [기록 계약](references/progress.md), 역할별 입력·확인 범위는 [역할 계약](references/reviewer-contracts.md)을 따른다.

## 명세의 내용

기존 문서 구성을 존중하고 필요한 내용만 보완한다.

- 요구: 사용자 목표와 정해진 동작·결과.
- 사례: 상황·행동·관측 결과를 번호로 연결한다. 결과를 가르는 결정과 실패·예외를 포함하며 실제 실행할 대표 사례는 구현 단계에서 고른다.
- 제약: 인터페이스·데이터·호환·실패 처리 등 만드는 방식을 묶는 결정.
- 범위 밖: 다루지 않기로 한 내용.
- 미정: 사용자 결정이 필요한 내용과 영향받는 요구.

명세는 구현의 제품 요구 기준이다. 승인 범위·결정 출처·검토 근거는 인계와 기록으로 함께 전달한다. 작업 로그를 제품 명세에 넣지 않는다. 사용자 요구와 에이전트 선택, 확인한 사실과 가정을 구분한다. 구현자가 요구를 유지하며 정할 세부사항까지 미리 고정하지 않는다.

검증 요구는 사용자 지정 범위·수단·환경·증거 조건을 보존한다. 기존 사례의 필요성·충분성·중복·과잉을 검토하되 서로 다른 동작을 같은 코드 경로라는 추측으로 삭제하지 않는다. 사용자 지정 검증의 축소·대체는 제안과 사용자 결정 대기로 남긴다.

## 작성·검토·수정

1. 기존 명세가 있으면 불필요한 선행 재작성 없이 첫 검토 대상으로 쓴다. 새 명세가 필요하면 Planner의 초안을 받아 부모가 저장한다. 위치는 사용자 지정·프로젝트 규칙을 우선하고 없으면 프로젝트의 명세 문서 위치를 선택해 알린다.
2. Planner Reviewer와 Programmer Reviewer에게 같은 버전과 사실 자료를 보내 독립 검토한다. 사용자 흐름·실패·예외와 요구의 코드 적용·판정 가능성을 확인한다. 미정으로 막힌 부분은 표시하고 나머지는 계속한다.
3. 부모가 지적을 통합하고 처리 방향·출처·근거를 정한다. Planner가 수정 문안을 반환하고 부모가 결정과의 일치를 확인해 저장·버전 부여한다.
4. 같은 리뷰어에게 지적별 답과 diff를 보내 해소와 변경 영향을 확인한다. 유효한 새 지적도 처리하며 반복 횟수로 종료하지 않는다. 리뷰어가 제안한 사례·제약을 명세에 반영했다면 그 최종 문안도 관련 축이 확인한다.
5. 두 축이 맡은 범위를 확인하고 같은 최종 명세에 열린 유효 지적·판정 보류가 없으면 인계한다. 그렇지 않으면 부분 결과와 필요한 결정을 구분한다.

검토만 요청이면 2의 결과와 추천 답·사례·제약 초안을 반환한다. 미정에 추천 답을 가정해 후속 흐름을 검토할 수 있지만 가정에 달린 지적을 구분하고 확정된 요구로 취급하지 않는다.

## 인계

- 기준 명세 경로·버전과 요구별 결정·변경 요약.
- 에이전트가 고른 주요 선택과 버린 대안·근거. 되돌리기 비싼 선택과 이견이 남은 결정을 먼저 설명한다.
- 두 축의 확인 범위·판정·근거, 사용자 결정 대기·확인하지 못한 부분.
- 사용자 검토가 필요한 사항. 구현을 시작한 것처럼 보고하지 않는다.
