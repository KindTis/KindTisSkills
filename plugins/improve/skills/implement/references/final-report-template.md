# 진행 기록과 완료 보고 계약

## Progress record

기록을 만들거나 재개할 때 [진행 기록 공통 계약](../../../references/progress-record.md)을 먼저 읽는다. 기록 위치·작성 원칙·지적 항목 형식은 그 문서를 따른다.

## Save checkpoints

| 단계 또는 사건 | 필요한 기록 |
|---|---|
| 준비·재개 | 승인 범위, 작업·기록 경로, 정본 명세·불변 snapshot, 관련 규칙, baseline·기존 사용자 변경, 개발 의존성/이후 수용 구분, 완료 기준, 현재 단계 |
| Main 판단과 필요한 설계 자문 | 지적 ID와 `ACCEPT`/`REJECT`/`MAIN_DECISION`/`DEFER`/`EXTERNAL_AUTHORITY_REQUIRED`, 이유·영향 요구·중요 가정. 수정을 제안한 상태와 실제 반영을 구분 |
| 불변 명세·계획 반영 | 입력 명세 경로·버전·해시, 명세 무변경 확인, 실제 계획 변경·요구→작업→검증 대응, Programmer 변경부 재검토 결과 |
| 계획·코드 단순화 | 각각의 독립 리뷰어·범위·snapshot·지적 ID/분류, Main 판단, 주 에이전트의 계획 반영과 Implementer의 코드 반영, Tester 영향 검사, 변경부 재검토. 계획 추정과 실제 코드 비교를 분리 |
| 구현 작업 | 완료·미완료 작업, 변경 파일과 동작, 중요한 판단·이탈, Implementer 본인 검사와 별도 Tester 검증을 구분 |
| 검증·실패 | 명령/절차·환경·revision/hash·exit status·가능한 pass/failure 수·산출물, 확인한 요구, 실패 조건·분류·재작업과 영향 재검증, 생략/미검증 이유 |
| 중단·인계·완료 | 현재 단계·완료 사항·실제로 막힌 개발 작업/근거·후속 절차, 개발 상태와 이후 사용자 수용·외부 승인·보고서 상태 |

지적 항목 예: 단일 저장 방식만 요구되는데 계획이 근거 없는 저장소 등록 팩터리를 제안했다면, `yagni` 지적과 Main의 채택 근거, 주 에이전트의 계획 수정과 Implementer의 해당 코드 반영, 실제로 바뀐 작업, 유지한 저장 실패 복구·회귀 검사와 변경부 재검토를 연결한다. “채택, 수정 완료”만으로 결과를 설명하지 않는다.

## Completion report

작업 규모에 맞춰 필요한 결과와 제약을 보고한다.

| 내용 | 보고할 사실 |
|---|---|
| 결과·상태 | `Complete`, `Partial`, `Blocked` 중 개발 상태와 결정 근거. 필수 검증 실패/미실행·필수 리뷰 누락이면 완료로 주장하지 않음. 이후 사용자 수용만 남은 경우 별도 상태 |
| 입력·요구 | 원본 요구, 정본 경로·최종 버전, 관련 규칙과 승인 범위, 요구 대응과 미충족 항목 |
| 독립 계획 검토·설계 판단 | Programmer 핵심 지적, Main의 계획 선택·거절·유보 결정과 이유·가정, 필요한 설계 자문, 저장 이력 링크 |
| 불변 명세·계획 수정 | 입력 명세의 전후 해시 일치, 계획에서 실제 바뀐 작업·파일·이유, 최종 계획 경로와 요구→작업→검증 대응 |
| 계획 단순화 | 별도 Programmer 계획 리뷰 범위·지적·판단·실제 계획 수정과 재검토. 절감은 추정 |
| 코드 단순화 | 별도 Programmer 리뷰 baseline·snapshot·task diff·미추적 신규 파일, 지적·판단·실제 수정·Tester 영향 검사·재검토. 순절감은 단순화 수정 전후 비교 근거로 표시하거나 미측정 |
| 구현 | 완료/미완료 작업, 변경 파일·핵심 동작·인터페이스/흐름, 중요한 계획 이탈, 실제 생성한 commit만 |
| 검증 증거 | 정확 명령 또는 재현 절차·환경·exit status·가능한 pass/failure 수·산출물·검증 요구, 실패/생략과 제약 |
| 미검증·후속 수용 | 실제 화면·입력·오디오·성능·장시간·외부 수용 등 실행하지 않은 범위, 구체적 개발 문제. 이후 사용자 수용은 owner·절차·기대 관찰·미완료 상태로 분리 |
| 최종 작업/보고 상태 | branch·worktree·dirty/clean·통합 상태·기록 절대 경로, 적용되는 구현 goal 완료 준비/배포 결과·보고 실패, 다음 사용자 소유 조치 |

계획의 `Lean already. Ship.`, 테스트 PASS 또는 단순화 검토를 누락한 코드 리뷰로 `CODE_REVIEW`를 대체하지 않는다. 유효한 cut 0건은 정상 결과다. 전체 기능 diff의 증감, 제안 절감, 단순화 수정의 실제 코드/test/config 변화는 구분하며 근거 없는 순절감을 발명하지 않는다.

## Evidence and completion boundaries

- 주 에이전트는 담당자의 성공 문구 외에 실제 변경 파일과 독립 리뷰·필수 검증 증거를 검토해 최종 완료를 판단하고 처리한다. 미결 설계 쟁점만 Advisor에게 자문하며 Advisor 최종 승인 게이트는 없다.
- 수정한 부분의 검사는 최종 tree에서 수행한다. 변하지 않은 검사는 당시 명령·결과·snapshot과 여전히 유효한 이유를 보존하고 새 실행으로 표기하지 않는다. 새로운 근거 없이 무변경 검사와 리뷰를 반복하지 않는다.
- 정적 검사, 빌드, 격리 테스트, E2E, 실제 화면/입력/오디오, 외부 서비스 수용을 구분한다. 다른 검사 통과가 누락된 실행 증거를 대체하지 않는다.
- 필수 빌드·회귀 실패를 근거 없이 기존 문제나 경고로 낮추지 않는다. 주 에이전트가 baseline·실패 증거와 Tester의 근거 분류로 구현·fixture/검사·환경 문제를 처리하고 담당자 원인 조사·수정과 영향 검사로 닫는다. 조사 결과 설계 변경·요구 재해석이 필요한 쟁점만 Advisor에게 자문한다.
- 개발 의존성이 없는 이후 플레이·선호 확인·출시 승인은 최종 인계로 둔다. 사용자 응답을 강제 기다리거나 그 이유만으로 개발 goal을 차단하지 않는다. 필수 검증의 실패·미실행을 이런 수용으로 바꿔 완료하지 않는다.
- 미관련 사용자 변경, ignore 상태와 인계 가능한 작업 환경을 보존한다. merge·push·배포·정리는 각 승인 범위에 따른다. Git이 없으면 branch·commit·worktree 작업이 없었음을 밝힌다.
- 주 에이전트는 메인 구현 goal 완료 전 적용되는 전역 `goal-completion-report` 패키지의 완료 준비를 수행하고 반환된 배포 결과를 최종 응답에 담는다. 구현 완료 보고서만 Cloudflare에 업로드하며 명세·계획·독립 검증·조사 문서에는 게시나 URL을 요구하지 않는다. 보고 실패는 개발 결과와 구분하고 패키지 또는 goal 도구의 실제 상태를 숨기지 않는다.
- 외부 제약으로 진행할 수 없으면 완료 작업·남은 문제·현재 단계와 증거를 인계한다. 새 근거 없이 같은 실패를 반복하지 않는다.
