# 불변 명세 기반 구현

## Core contract

사용자가 지정한 확정 명세를 불변 입력으로 삼는다. 이 스킬은 명세 확인 → 구현 계획 작성 → 프로그래머 독립 계획 리뷰 → 구현 → 코드 리뷰·검증을 수행한다. 명세 리뷰·조정·개선 단계는 `improve:spec`에 있으며 이 구현 흐름에 포함하지 않는다. 별도로 확정된 명세도 직접 입력받을 수 있고 `improve:spec`의 선행 실행을 요구하지 않는다.

명세의 정본과 입력 스냅샷을 모든 역할이 변경하지 않는다. 입력 경로·버전·해시를 보존하고 최종 검증에서 원본과 일치하는지 확인한다. 명세 자체의 모순·필수 누락으로 진행할 수 없으면 영향받는 작업과 필요한 결정을 반환한다. 해당 문제를 해결하기 위해 명세를 직접 수정하거나 자동으로 명세 개선 스킬을 실행하지 않는다. 독립적인 승인 작업은 계속한다.

사용자 지시와 전역·프로젝트 규칙이 우선한다. 승인된 목표 안의 구현 방식·계획·코드 수정과 필요한 검증은 반복 승인 없이 완료하고, 새 범위나 권한이 필요한 작업만 확인한다.

## Roles and dispatch

[공유 역할과 위임](../../references/roles-and-dispatch.md)을 따른다. 주 에이전트가 불변 명세를 기준으로 구현 계획과 진행 기록을 직접 작성·수정한다. 계획 작성이 끝난 뒤 새 독립 Programmer가 계획을 검토한다. 실제 구현은 Implementer에게 위임한다. 구현 후에는 계획 리뷰어와 별개의 새 독립 Programmer가 실제 코드 변경을 검토하고 Tester가 검증한다. Planner의 명세 리뷰나 계획 작성자의 자체 검토는 Programmer 독립 계획 리뷰를 대신하지 않는다.

## Workflow

아래 의존 순서를 지킨다. 불변 명세와 현재 변경·시험·환경에 여전히 유효한 증거는 재사용한다. 의미 있는 미해결 질문·실제 수정·새 증거로 영향받은 검사와 리뷰만 갱신하며, 새 근거 없이 같은 검토·검증을 반복하지 않는다.

| 단계 | 실행과 완료 기준 |
|---|---|
| `PREPARE` | 승인 범위·관련 규칙·확정 명세·기존 구현·실행 환경·필요 검증을 확인한다. 명세 경로·버전·해시와 불변 스냅샷, task baseline·기존 사용자 변경을 기록한다. 실제 개발 의존성과 이후 사용자 수용을 구분한다. 명세를 다시 제품성 리뷰하거나 보정하지 않는다. |
| `PLAN_WRITING` | 주 에이전트가 불변 명세를 기준으로 구현 방향·작업 분해·완료 기준을 정하고 구현 계획서를 직접 작성한다. 명세 버전·해시, 요구→작업→검증 대응, 경로·인터페이스·데이터 흐름·실패 동작, 필요한 재현·검증 명령을 담는다. 이후 사용자 수용은 별도 인계로 둔다. |
| `PLAN_REVIEW` | 계획 작성 후 새 Programmer가 명세 충족·기술 타당성·구조·실패 동작·검증 대응과 원본 단순화 기준으로 계획을 독립 검토한다. 테스트 계획은 전역 검증 지침의 Advisor 자문 결과를 재사용해 계획 반영과 요구 대응을 확인하며, 같은 테스트 타당성·중복·병합 판단을 반복하지 않는다. 주 에이전트가 채택 지적을 계획에 직접 반영하고 Programmer가 변경부를 재검토한다. 명세를 수정해서 지적을 해결하지 않는다. 중요한 미결 사항을 해결하기 전 구현을 시작하지 않는다. |
| `DELEGATED_IMPLEMENTATION` | 안전한 작업 환경을 확인하고 최종 계획의 의미 있는 작업 단위를 Implementer에게 맡긴다. 관련 실패 재현과 꼭 필요한 격리 테스트는 구현 수정 전에 준비한다. 승인 목표 안의 기술 선택은 Implementer가 자율적으로 하되 새 설계 판단·범위 확대·명세를 충족할 수 없는 쟁점은 근거와 함께 부모에게 반환한다. |
| `CODE_REVIEW` | 새 Programmer가 실제 task diff와 미추적 신규 파일까지 명세·계획 적합성, 정확성·보안·성능·회귀와 단순화 관점에서 독립 검토한다. 주 에이전트 판단·지시→Implementer 수정→Tester 영향 검사→리뷰어 변경부 재검토로 채택 사항을 닫는다. 계획 리뷰나 테스트 PASS로 코드 리뷰를 대신하지 않는다. |
| `VERIFICATION` | Tester가 승인 범위의 필수 E2E·빌드·회귀 및 필요한 보조 검사를 실행하고 재현 가능한 증거를 반환한다. 주 에이전트가 증거와 Tester의 근거 분류로 구현·fixture/검사·환경 문제를 처리하고 담당자의 원인 조사·수정과 영향 재검증을 조정한다. 입력 명세의 해시가 그대로인지 확인한다. 이후 수정은 영향받은 계획·코드 리뷰와 검사만 갱신한다. |
| `FINAL_REPORT` | 주 에이전트가 실제 결과 파일과 독립 리뷰·필수 검증·명세 불변 증거로 완료를 판단한다. 필수 개발 검증 실패는 `Complete`로 표시하지 않는다. 한국어 기록에 결과를 직접 반영하고 적용되는 구현 goal 보고 절차 후 기존 goal을 완료·인계한다. |

## Simplicity boundaries

계획·코드 단순화는 `delete`, `stdlib`, `native`, `yagni`, `shrink` 근거를 사용한다. 명시 요구, 최소 회귀·smoke 검사, 필수 복구, 보안·개인정보·성능·플랫폼 제약, 호환·마이그레이션, 실제 소비자로 정당화된 구조를 보존한다. 관련 호출처를 확인하고 task baseline과 기존 사용자 변경을 구분하며 관련 없는 정리는 하지 않는다. ignore 상태를 보존한다.

각 리뷰의 지적·Main 판단·실제 수정·영향 검사·재검토를 추적하며 필요한 설계 자문만 연결한다. 계획 절감은 추정, 코드 절감은 단순화 수정 전후의 실제 비교로 구분한다. 측정 근거가 없으면 미측정으로 기록한다. 유효한 삭제가 0건이어도 완료할 수 있으며 줄 수 감축을 만들기 위해 동작이나 검증을 없애지 않는다.

## Verification and completion

E2E를 기본·우선 검증으로 사용하고 검증 효과에 맞는 규모를 선택한다. 사용자 작업을 방해하지 않는 헤드리스·백그라운드·분리 환경에서 실행하며 실사용 데이터와 브라우저 프로필을 분리한다. GUI 포커스·키보드·마우스·오디오·알림에 영향이 불가피하면 영향과 필요성을 설명하고 그 실행의 승인을 받는다. 방해 없는 검증은 계속한다.

Tester는 제품 소스를 수정하거나 통과를 위해 테스트·완료 기준을 완화하지 않는다. 승인 범위의 격리 fixtures와 검증 산출물 작성은 가능하다. 필수 빌드·회귀 실패와 구현 결함은 개발 작업으로 남긴다. 정적 검사·빌드 통과를 실제 화면·입력·오디오 검증으로 주장하지 않는다.

사용자가 나중에 수행할 플레이·선호 확인·출시 승인은 실제 미완료 개발 작업의 의존성과 구분한다. 개발과 필수 검증이 끝났다면 산출물·절차·기대 관찰·미검증 상태를 최종 인계하고 응답을 강제 대기하지 않는다. 필수 검증을 수행할 수 없는 제약은 정확히 보고하며 사용자 수용으로 바꿔 완료를 주장하지 않는다. 외부 제약의 같은 실패를 새 근거 없이 반복하지 않는다.

메인 구현 goal 완료 준비와 배포 결과 보고는 전역 `goal-completion-report` 패키지와 [완료 보고 경계](references/final-report-template.md#evidence-and-completion-boundaries)를 따른다.

## Helper skills

필요한 단계에서 사용 가능한 도움 스킬의 관련 부분만 적용한다. `writing-plans`는 불변 명세에 따른 계획 작성, `executing-plans`는 Implementer의 승인 작업 실행, `using-git-worktrees`는 필요한 안전한 작업 환경 확인에 사용한다. 도움 스킬이 명세 수정·명세 리뷰 추가·리뷰어 변경·재위임·조기 통합을 요구하면 해당 단계에 적용하지 않는다. 단순화는 사용 가능한 `ponytail-review`/`ponytail` 또는 위 동등 기준을 사용한다. 검증·통합 도움 지침은 이미 승인된 범위에서만 적용하며 merge·push·cleanup 권한을 확대하지 않는다. 도움 스킬의 미설치 자체로 전체 작업을 멈추지 않고 필요한 역할·입력·증거·권한을 생략하지 않는다.
