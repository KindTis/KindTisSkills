# 확정 명세 구현·개선

Architect의 계획 검토·개선 후 Implementer와 시각 작업의 Art Painter가 구현하고, 필요한 코드 리뷰·실행 검증·시각 검수의 결과로 수정과 완료를 판단한다.

## 범위와 입력

사용자 승인 범위와 확정 명세를 확인한다. 명세 경로·버전·해시를 기록하고 불변 입력으로 보존한다. 명세를 바꿔야 하는 문제는 영향과 필요한 결정을 반환하며 어느 역할도 임의로 명세를 고치거나 명세 개선을 시작하지 않는다.

사용자가 지정한 작업 공간, 없으면 현재 공간을 사용한다. baseline·기존 사용자 변경을 구분하고 merge·배포·정리는 승인 범위에서만 한다. 계획만 요청됐으면 계획 인계에서 끝낸다.

준비 때 [위임 계약](../../references/delegation.md), [리뷰 계약](../../references/review-contract.md), [역할 계약](references/reviewer-contracts.md), [기록 계약](references/progress.md)을 읽는다. 적용되는 전역·프로젝트·사용자 지정 검증 요구를 확인해 계획에 반영한다. 검증 수단은 적용 지침을 따르며 E2E를 일괄 추가하지 않는다.

## 계획 개선

1. Architect가 실제 코드에 근거한 작업·순서·의존성·필요한 기술 선택과 검증 준비를 제안한다. 명세 사례가 없으면 요구에서 사례를 제안하고 부모가 선택 근거를 기록한다. 시안을 재현하는 작업과, 모양·배치·스타일이 값으로 주어지지 않아 보면서 정해야 하는 작업은 Art Painter 담당으로 구분한다. 명세가 시각 작업으로 지정한 부분은 그대로 따른다. 한 작업에 섞여 있으면 보면서 정할 부분(배치 데이터·스타일 값·에셋)과 그것을 쓰는 코드를 나눈다. 값이 명세된 변경과 기존 구성 요소의 조립은 Implementer가 맡는다. 판정할 화면·상태를 캡처하는 수단을 계획에 두고 시각 작업보다 먼저 준비하며, 시안이 있으면 시안과 같은 시점·범위로 맞춘다. 캡처 수단은 실제 실행 화면을 목표 해상도·표시 설정 그대로 손실 없이 얻는 것이어야 한다.
2. 부모가 계획을 저장·버전 부여하고 Programmer Reviewer와 Tester에게 같은 계획과 관련 기존 검증 근거를 보낸다. 요구별 전제조건·관측값과 기존 근거가 입증하지 못한 부분을 대조해 추가 실행의 수단·환경·범위를 검토한다. Tester는 실행 가능성이나 사용자 방해 여부가 불확실한 필수 검증을 승인 범위의 작은 대표 사례로 먼저 확인한다. 구현 후에만 확인할 수 있는 항목은 확인 시점·조건을 계획에 남기며 지적을 반영해 재검토한다.
3. 결함이면 먼저 재현을 시도한다. 재현되지 않으면 원인 근거와 안전한 수정 가능성·검증 한계를 평가한다. 근거가 충분한 승인 범위의 수정은 진행하며 기대 동작·범위·권한의 불명확성만 사용자 결정으로 반환한다.
4. 계획의 요구별 작업·의존성과 시각 작업의 Art Painter 배정, 검증 목록과 실행 조건을 확인했고 열린 유효 지적·판정 보류가 없으면 구현한다.

시각 작업의 합격 기준은 Art Director가 제안하고 부모가 계획과 함께 저장한다. 시안이 있으면 시안에서 필수 요소와 스타일 참고를 구분하고, 시안이 다루지 않는 부분은 명세의 시각 요구만 판정할 수 있는 항목으로 옮긴다. 명세가 판정할 수 있는 기준을 이미 정했으면 그대로 쓴다. 같은 기준을 Art Painter의 입력과 검수에 쓴다. 캡처 수단이 준비되면 Art Director가 시각 작업 전에 직접 실행해 실제 화면대로 보이는지 확인한다.

동작을 바꾸지 않는 문서·주석만의 작업은 Programmer Reviewer의 diff 검토로 계획·변경·인계를 마치며 Tester 실행을 추가하지 않는다. 프롬프트처럼 문서 자체가 동작을 바꾸면 해당 행동 확인을 준비한다.

## 구현·리뷰·재작업

- Implementer는 검토된 계획을 구현하고 필요한 자체 확인 결과를 반환한다. Art Painter는 계획이 배정한 시각 작업을 합격 기준과 함께 받아 같은 흐름으로 구현하며, 시안이 있으면 원본을 함께 받는다. 부모가 대상 상태를 식별해 코드 리뷰와 검증에 전달한다.
- Programmer Reviewer는 baseline 대비 task-owned 변경 전체와 미추적 신규 파일을 요구·제약에 대조한다. Tester는 필수 사례를 실행하거나 현재 대상에 유효한 기존 증거를 확인해 재사용한다.
- 코드 결함·국소 선택은 Implementer가, 시각 결과의 결함은 Art Painter가, 맡은 검사·fixture는 Tester가 수정한다. 구조·의존성에 영향을 주는 계획 결함은 Architect가 수정 문안을 내고 부모가 저장한 뒤 영향받은 계획 검토·검증 목록을 재확인한다.
- 부모는 추가 작업이 미확인 필수 요구를 입증하거나 관측된 결함·회귀·실제 부작용을 해소하는 데 필요한지 판단한다. 기존 대체 수단·최소 추가 구현·미확인 인계 중 적절한 경로를 선택하고 작업 범위를 배정한다.
- 부모는 영향받은 판정자에게 지적별 답·변경·근거를 보내 재확인을 요청한다. 대상 상태와 쓰기 경계는 위임 계약을 따른다.
- 권한·환경 때문에 진행할 수 없는 항목은 부모가 기존 승인·관련 근거·대체 수단을 대조해 요구와 명시된 검증 조건을 유지할 수 있는지 판단한다. 유지할 수 없는 필수 항목은 미검증으로 남기고, 사용자 결정이 필요한 잔여 쟁점만 독립적인 승인 작업을 마친 뒤 영향·대안과 함께 모아 반환한다.

부모는 필수 사례 전체를 현재 근거와 대조해 확인 완료·미실행·근거 부족·실패를 구분한다. 일부 실행 성공이나 담당자의 요약만으로 남은 필수 작업을 확정하지 않는다. 기존 진행 기록에서 변경·새 결과·새 지적의 영향 항목을 갱신하며 별도 최종 감사 단계를 추가하지 않는다.

## 시각 검수

사용자가 시각 요소 생성·변경 작업의 검수를 요구했거나 Art Painter가 구현한 결과라면 해당 요소는 반드시 Art Director 검수를 받는다. 부모가 필요성이 낮다고 생략하지 않는다. 별도 지시가 없어도 시각적 완료 기준이나 실제 변경 영향상 독립 품질 판단이 필요하면 적용한다.

부모가 대상 화면·상태, 승인된 참조·방향·필수 요소를 전달한다. Art Director가 계획의 캡처 수단으로 실행 화면을 직접 보고 판정한다.

부모는 Art Director의 필수 지적을 원문과 근거 캡처 그대로 그 결과를 만든 담당에게 배정하고, 수정 내용과 결과를 볼 방법을 Art Director에게 돌려 직접 재검수하게 한다. 시각 결과의 확인과 피드백은 합격할 때까지 두 역할 사이에서 반복한다.

## 완료와 인계

부모는 다음을 종합한다.

- 확정 명세의 요구·제약을 충족하고 필수 검증이 통과했다.
- 해당 리뷰어가 맡은 범위를 확인했으며 열린 유효 지적·판정 보류가 없다.
- 코드 검토·검사·시각 판정의 대상과 근거가 최종 변경에도 유효하다.
- 명세 원본 해시가 유지된다.

완료·부분·진행 불가를 구분해 변경 요약, 주요 기술 선택·계획 이탈, 사례별 수단·명령·대상 상태·결과·증거 위치와 재사용 여부, 작업 공간·브랜치를 반환한다. 남은 사용자 인수·선호 확인·출시 승인은 별도로 표시하며 필수 미검증을 이 항목으로 바꿔 완료하지 않는다.
