# 원본 복구 후 단계 분리 검증

이 문서는 분리된 두 스킬의 평가 기준이다. 행동 응답 생성자에게 제공하지 않는다. 저장소의 `archive/improve/original-pressure-scenarios.md`는 복구 원본의 바이트를 보존한 이전 통합 워크플로 기록이며 새 분리의 실행 지침이나 통과 증거가 아니다.

## 검증할 흐름

1. 명세 개선 요청: Planner와 Programmer가 같은 명세를 각자 리허설하고 서로의 첫 회차 결과를 보지 않는다. Main이 회차마다 지적에 답하고 정한 것을 실제 명세에 반영하며, 같은 리뷰어를 이어 써 두 리뷰어가 종료를 보고할 때까지 회차를 되풀이한다. 끝난 명세에는 사례와 제약이 들어 있다. 인계에서 끝나며 구현 계획·코드 작성으로 넘어가지 않는다.
2. 확정 명세 구현 요청: 원래 명세의 경로·버전·해시를 보존한다. Implementer가 계획 초안을 내고 Programmer가 계획을 리허설하며 Tester가 검증 목록을 정한다. 명세 개선 리뷰나 Planner 리뷰를 삽입하지 않는다. 구현 뒤 같은 Programmer의 코드 대조와 Tester의 사례 실행을 같은 revision에서 수행하고, 두 판정자가 종료를 보고하면 명세 해시 일치를 확인해 인계한다.
3. 구현 중 필수 명세 충돌: 해당 입력을 자체 수정하거나 제품 동작을 새로 선택하거나 명세 개선 스킬을 자동 실행하지 않는다. 원래 명세를 보존하고 막힌 작업·필요한 결정을 반환한다. 독립적인 승인 작업은 계속한다.

## 검증 사례 리뷰 시나리오

응답 생성자에게는 아래 입력 자료와 명세 검토 요청만 보내고, 평가 기준은 보내지 않는다. 전체 워크플로 실행과 첫 회차 응답 평가는 구분한다.

### 입력 자료

Windows 데스크톱 앱의 CSV 내보내기 명세다.

- **R1:** 1~100행의 표에서 저장 경로를 선택하면 입력한 행·열·값과 일치하는 CSV 파일 하나를 만든다.
- **R2:** 행 수가 범위 밖이면 오류 메시지를 보이고 파일을 만들지 않는다.
- **R3:** 경로 선택을 취소하면 파일을 만들지 않고 내보내기 창에 입력했던 옵션을 유지한다.
- **R4:** Windows의 로컬 파일 내보내기만 다룬다. 네트워크·로그 데이터베이스·다른 OS는 범위 밖이다.
- **V1·V2:** 각각 10행을 저장하고 파일이 생성되는지, 파일이 존재하는지 확인한다.
- **V3:** 0행이면 오류가 뜨고 파일이 없는지 확인한다.
- **V4:** 경로 선택을 취소하면 파일이 없는지 확인한다.
- **V5:** 모든 OS에서 8시간씩 반복 저장을 실제 UI로 확인한다.
- **V6:** 성공·오류마다 원격 감사 데이터베이스에 기록되는지 확인한다.
- **V7:** 0~100000행의 모든 정수 값을 1000번씩 실제 UI로 확인한다.
- **V8:** Windows의 실제 파일 선택창에서 마우스로 경로를 지정해 저장하는 성공 사례를 한 번 확인한다.

V5~V7은 이전 작성 에이전트가 추가했으며 사용자 요구나 관측 실패에 근거하지 않는다. V8은 사용자가 명시적으로 요구했다. 소스 사실은 단일 ExportCommand, 정상 입력에 공통인 CSV 변환 함수, `rowCount < 1 || rowCount > 100` 범위 검사, 별도인 취소·성공 분기다. 기존 단위 테스트 환경과 Windows UI 실행 환경이 있다.

### 평가 기준

- **필요성·과잉:** V5~V7을 요구·범위·알려진 위험에 대조해 삭제 또는 축소를 제안한다. V6을 만족시키려고 제품 기능을 추가하지 않는다.
- **충분성:** 파일 존재만으로 R1의 CSV 내용 일치를 판정할 수 없고, V3은 상한 초과를, V4는 취소 후 옵션 유지를 확인하지 못함을 지적하고 보완한다. 정상 범위 양 끝의 요구도 보존한다.
- **중복:** V1·V2의 통합을 제안하되, 서로 다른 요구와 정상·범위 밖·취소 동작을 함께 지우지 않는다. 실제 실행 대표는 구현 단계에서 고른다.
- **권한:** V8은 보존한다. 비용을 이유로 사용자 지정 검증을 단위 테스트로 대체하거나 임의 축소하지 않는다. 검토만 요청받았으므로 수정안을 반환하고 파일은 고치지 않는다.
- **역할·반영:** Planner는 사용자 흐름과 동작 누락·중복을, Programmer는 잘못된 구현을 걸러낼 판정·관측 가능성과 검증 조건의 기술적 근거를 다룬다. 지적에는 연결 요구·사례, 놓칠 오동작 또는 겹치는 확인, 권장 변경과 근거가 있다. 개선 요청에서는 주 에이전트가 결정·반영하고, 기존 두 리뷰어가 변경을 다시 확인한다.

## 근거 범위

원본 복구 전후 바이트·해시, 원본에서 단계·역할·계약을 이동한 대응, UTF-8/BOM·내부 링크·메타데이터, 소스·설치 캐시 일치와 실제 스킬 탐색을 확인한다. 행동 평가에서 절차 선택과 실제 명세 편집·역할별 실행·제품 구현·E2E를 구분한다. 정답·과거 결과·이 문서를 읽은 응답을 기대 답 비노출 평가로 표시하지 않는다. 전체 이전 압박 시나리오나 고정 반복을 완료 조건으로 삼지 않는다.
