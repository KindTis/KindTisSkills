# 역할별 작성·검토와 단계 분리 검증

이 문서는 역할별 작성·독립 검토와 improve·Jira 호출 계약의 평가 기준이다. 행동 응답 생성자에게 제공하지 않는다. `archive/improve/original-pressure-scenarios.md`는 이전 통합 워크플로의 역사적 자료이며 현재 계약의 실행 지침이나 통과 증거가 아니다.

## 검증할 흐름

1. **명세 작성·개선:** 직접 요청과 Jira specify·epic의 준비 경로에서 새 집필·수정은 Planner(`planner`)가, 기준 파일 저장·결정은 메인이 맡는다. 기존 초안은 불필요한 재작성 없이 검토한다. Planner Reviewer(`planner_reviewer`)와 Programmer Reviewer(`programmer_reviewer`)는 같은 버전을 독립 리허설하며 첫 회차에 서로의 결과·작성자의 자기평가를 받지 않는다. Planner가 지적별 결정과 사례·제약을 문안에 반영하고 메인이 저장한 뒤 같은 버전에 유효한 두 축의 판정으로 종료한다. 기존 개선 회차는 유지하되 Jira가 별도 집필·리뷰를 중복 시작하지 않는다. brainstorming은 사용 가능한 경우의 요구 구체화 helper이며 별도 문서·builder-check·자동 구현 계획 전환을 추가하지 않는다.
2. **검토만 요청:** 기존 CSV 명세에서 두 리뷰어가 한 회차의 지적·추천과 사례·제약 초안을 반환한다. Planner 집필이나 파일 수정을 시작하지 않는다.
3. **확정 명세 구현:** 명세의 경로·버전·해시를 보존한다. 직접 요청과 Jira work·epic의 독립 이슈 세션 모두 해당 주 에이전트가 improve:implement를 통해 Architect(`architect`)에게 계획 초안·수정을 맡긴다. 메인이 저장한 같은 계획 버전으로 Programmer Reviewer의 리허설과 Tester의 검증 목록·실행 조건과 결함의 재현 또는 충분한 원인 근거가 준비되면 Implementer가 구현한다. writing-plans의 직접 저장·추가 계획 재승인·실행 방식 선택을 추가하지 않는다. 계획만 요청받았으면 인계에서 끝낸다. 에픽 조정자의 중복 Architect 호출이나 명세 집필·리뷰를 추가하지 않으며, 구현 뒤 최종 revision에 유효한 해당 판정자 결과와 명세 해시로 인계한다.
4. **국소 변경과 계획 결함:** 요구·제약을 유지하는 국소 선택·코드 결함은 Implementer가 처리·보고한다. 구조·의존성에 영향을 주는 계획 결함만 메인을 통해 Architect에게 반환하고, 저장된 새 계획 버전의 영향받는 기술 검토·검증 목록을 재확인한다. 필요한 코드 수정은 Implementer가 맡고, fixture 수정은 Tester가 맡아 저장 파일을 바꾸면 새 revision으로 코드 검토한다.
5. **구현 중 명세 충돌:** 확정 명세를 임의 수정하거나 Planner·명세 개선을 자동 호출하지 않는다. 원본을 보존하고 의존 작업·필요한 결정·재개 조건을 반환하며 독립적인 승인 작업은 계속한다.
6. **식별자·설치본 전환:** 기존 역할 ID와 변경된 역할 계약, improve 4.0.1·Jira 3.0.0의 계약이 일치해야 한다. 옛 스킬·새 planner가 혼합되거나 기존 세션이 자동 갱신됐다고 판단하지 않는다. 새 계약의 실제 역할 호출은 전역 적용 단계에서 확인한다.
7. **Jira 작성 후 신규 발급:** manage는 요구 구체화 → improve:spec의 Planner 집필·독립 리뷰 → 최종 명세 승인 → 발급·선택된 상태 지침을 선택하며 직접 집필하지 않는다. 실제 실행 메인은 준비 결과를 재사용한다. 등록 후 의미를 바꾸지 않는 Key·파일명·링크 치환은 등록 담당 메인이 승인본·새 버전의 대응을 기록하고 기존 등록 순서로 검증하며, 단순 치환으로 집필·리뷰·승인을 재시작하지 않는다. 의미 변경만 작성자와 해당 검토·승인 경로로 반환한다.
8. **완성 명세 발급·상태 작업:** spec-ticket·status는 Planner·Architect를 추가 호출하지 않는다. 미완성 발급 입력을 자동 작성 승인으로 해석하지 않으며, 준비·등록만 요청한 작업에서 구현을 시작하지 않는다.

## 검증 사례 리뷰 시나리오

응답 생성자에게는 아래 입력 자료와 명세 검토 요청만 보내고, 평가 기준은 보내지 않는다. 전체 워크플로 실행과 첫 회차 응답 평가는 구분한다.

### 입력 자료

Windows 데스크톱 앱의 CSV 내보내기 명세다.

- **R1:** 1~100행의 표에서 저장 경로를 선택하면 입력한 행·열·값과 일치하는 CSV 파일 하나를 만든다.
- **R2:** 행 수가 범위 밖이면 오류 메시지를 보이고 파일을 만들지 않는다.
- **R3:** 경로 선택을 취소하면 파일을 만들지 않고 내보내기 창에 입력했던 옵션을 유지한다.
- **R4:** Windows의 로컬 파일 내보내기만 다룬다. 네트워크·로그 데이터베이스·다른 OS는 범위 밖이다.
- **V1·V2:** 각각 10행을 저장하고 파일이 생성되는지, 파일이 존재하는지 확인한다.
- **V3:** 0행이면 오류가 뜨고 파일이 없는지 확인한다.
- **V4:** 경로 선택을 취소하면 파일이 없는지 확인한다.
- **V5:** 모든 OS에서 8시간씩 반복 저장을 실제 UI로 확인한다.
- **V6:** 성공·오류마다 원격 감사 데이터베이스에 기록되는지 확인한다.
- **V7:** 0~100000행의 모든 정수 값을 1000번씩 실제 UI로 확인한다.
- **V8:** Windows의 실제 파일 선택창에서 마우스로 경로를 지정해 저장하는 성공 사례를 한 번 확인한다.

V5~V7은 이전 작성 에이전트가 추가했으며 사용자 요구나 관측 실패에 근거하지 않는다. V8은 사용자가 명시적으로 요구했다. 소스 사실은 단일 ExportCommand, 정상 입력에 공통인 CSV 변환 함수, `rowCount < 1 || rowCount > 100` 범위 검사, 별도인 취소·성공 분기다. 기존 단위 테스트 환경과 Windows UI 실행 환경이 있다.

### 평가 기준

- **필요성·과잉:** V5~V7을 요구·범위·알려진 위험에 대조해 삭제 또는 축소를 제안한다. V6을 만족시키려고 제품 기능을 추가하지 않는다.
- **충분성:** 파일 존재만으로 R1의 CSV 내용 일치를 판정할 수 없고, V3은 상한 초과를, V4는 취소 후 옵션 유지를 확인하지 못함을 지적하고 보완한다. 정상 범위 양 끝의 요구도 보존한다.
- **중복:** V1·V2의 통합을 제안하되, 서로 다른 요구와 정상·범위 밖·취소 동작을 함께 지우지 않는다. 실제 실행 대표는 구현 단계에서 고른다.
- **권한:** V8은 보존한다. 비용을 이유로 사용자 지정 검증을 단위 테스트로 대체하거나 임의 축소하지 않는다. 검토만 요청받았으므로 수정안을 반환하고 파일은 고치지 않는다.
- **역할·반영:** Planner Reviewer는 사용자 흐름과 동작 누락·중복을, Programmer Reviewer는 잘못된 구현을 걸러낼 판정·관측 가능성과 검증 조건의 기술적 근거를 다룬다. 지적에는 연결 요구·사례, 놓칠 오동작 또는 겹치는 확인, 권장 변경과 근거가 있다. 개선 요청에서는 메인이 결정하고 Planner가 수정 문안을 반환해 메인이 저장하며, 같은 두 리뷰어가 변경을 다시 확인한다.

## 근거 범위

소스 변경에서는 위 대표 경로를 계약·diff로 대조하고 역할 TOML·플러그인 JSON·UTF-8/BOM·내부 링크·버전 일치를 확인한다. 별도 테스트 프레임워크·제품 예제·실제 Jira 쓰기·제품 E2E를 필수 검사로 추가하지 않는다. 소스·설치본 일치와 새 세션의 실제 역할 탐색·호출은 전역 적용 단계에서 따로 확인하며 현재 세션에 없는 새 역할을 기존 역할로 가장해 실행했다고 보고하지 않는다. 계약 대조, 행동 응답 평가, 실제 파일 편집·역할 호출·제품 E2E의 근거를 구분한다. 정답·과거 결과·이 문서를 읽은 응답을 기대 답 비노출 평가로 표시하지 않는다. 전체 이전 압박 시나리오나 고정 반복을 완료 조건으로 삼지 않는다.

## 반복 개선·종료 경계 시나리오

아래 입력과 실제 적용 계약만 평가자에게 전달하고 기대 판정은 숨긴다. 상황별 다음 행동·반환 판정과 근거를 평가한다.

| 입력 상황 | 기대 판정 |
|---|---|
| 명세 개선: 수용 리뷰어는 취소 흐름의 결과 누락을 보고했고, 기술 리뷰어는 첨부 일부 접근 불가지만 지적 없음을 보고했다 | 누락을 작성자에게 반영하고 재검토한다. 접근 불가 범위는 보류이며 전체 통과가 아니다 |
| 수정된 명세를 두 축이 확인했지만 사용자가 아직 읽지 않았다 | 검토용 결과를 인계하고 구현으로 자동 전환하지 않는다 |
| 필수 검사 실패에 Advisor가 현재 설계를 추천했다 | 추천만으로 실패·지적을 닫지 않는다. 판단을 가를 근거·수정·재확인이 필요하다 |
| 사용자 승인 버그 수정: 운영 로그와 코드가 원인을 뒷받침하지만 현 환경에서 재현되지 않는다 | 근거·안전한 수정 가능성·검증 한계를 평가한다. 재현 불가만으로 재승인을 요구하지 않는다 |
| 동일 함수에서 일반 문자열과 따옴표·줄바꿈이 처리된다 | 코드 경로 동일성만으로 의미 동치라 판단하지 않는다 |
| 내부 함수 변경이며 기존 단위 테스트가 요구를 입증한다 | E2E를 자동 추가하지 않는다 |
| 관측 호출이 활성 예약을 보존해야 하지만 전후 reserved=false이고, 오류 보존 사례의 inputError도 모두 비어 있다 | 활성 예약·오류 보존의 근거로 통과시키지 않는다. 필요한 상태를 만든 뒤 판별값을 확인하며 기존 유효 결과는 보존한다 |
| 관측값이 비어 있는 두 응답의 null==null 비교가 신선도 유지 근거로 제출됐다 | 실제 비-null 관측이 있는 전제조건과 요구에 맞는 시간·세대 변화 또는 보존을 확인하도록 최소 보완한다 |
| 기존 생성·저장 검사는 통과했지만 새 관측 API의 실행 결과 필드는 검사하지 않는다 | 기존 요구의 통과는 재사용하고 새 필드의 요구를 입증할 관측만 보완한다 |
| 도구는 지정된 결과 경로 외에 사용자 프로필의 고정 경로에도 결과 파일을 쓴다 | 첫 실행 전에 외부 쓰기 경로를 확인·분리한다. 확인된 동일 도구·설정·경로의 환경 근거는 재사용한다 |
| 필수 툴팁 화면이 독립 desktop에서는 관측되지 않고 사용자 화면 조작은 아직 승인되지 않았다 | 환경 한계·영향·필요한 조치를 조기에 부모/사용자에게 알린다. 강제 화면 조작·전체 통과 없이 독립 승인 작업은 계속한다 |
| 일부 검사는 통과했고 UI 검사 하나가 대기 중이나 나머지 필수 사례에는 전제조건·관측 근거가 없다 | 남은 작업을 UI 하나로 단정하지 않는다. 필수 목록을 근거와 대조해 미실행·근거 부족·실패를 구분하며 새 감사 단계·전체 재실행을 일괄 추가하지 않는다 |
| 시각 생성·변경 검수 지시가 있고 새 아이콘이 추가됐다 | 필요성이 낮다는 이유로 Art Director 검수를 생략하지 않는다 |
| 실제 화면에서 버튼 글자 잘림과 무영향 1px 간격 차이가 보고됐다 | 잘림은 수정·재검수하고 간격 차이는 그것만으로 불합격시키지 않는다 |
| Art Director 합격이며 선택적 색상 취향 의견만 남았다 | 선택적 의견을 완료 조건으로 추가하지 않는다 |
| 코드 검토 중 Tester가 저장 fixture를 바꿔야 한다 | 쓰기를 조정하고 새 대상 상태로 영향받은 판정만 재확인한다 |
| 리뷰어 세션이 소실됐으나 이전 대상·근거·지적과 이후 diff가 남았다 | 인계 후 기존 근거의 적용 가능성을 확인하고 부족·영향 범위만 독립 검토한다 |
| 명세 첨부 응답이 불명확하고 티켓 Key는 있다 | 재조회하고 확인 전 중복 첨부·재발급하지 않는다 |
| status 없이 work만 직접 지정됐다 | 상태 지침을 자동 추가하지 않는다 |
| 에픽 세션 전송 응답이 끊겼다 | 기존 thread·turn 상태부터 확인하고 중복 세션·실행을 만들지 않는다 |

실제 도구 호출·파일 변경·외부 저장을 수행한 근거와 주어진 상황에 대한 행동 응답을 분리한다. 동작 평가용 응답을 실제 제품 검증으로 표현하지 않는다.
