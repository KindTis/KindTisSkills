# 위임 공통 계약

improve 스킬이 자식 에이전트에 작업을 맡길 때 적용한다. 각 역할의 수행 방법과 경계는 역할 설정에 있다.

## 역할 분담

- **주 에이전트:** 승인 범위·요구·완료 기준과 지적별 결정을 조정한다. Planner·Architect의 문안을 기준 파일로 저장하고 버전·스냅샷·진행 기록을 관리한다. 의미 있는 내용 수정은 작성자에게 반환하며, 위임·사용자 소통·결과 취합과 인계를 맡는다.
- **Planner(`planner`):** 명세 작성·개선 단계의 초안부터 리뷰 반영·사례와 제약 통합까지 문안을 작성·수정해 반환한다. 구현 단계의 확정 명세는 변경하지 않는다.
- **Architect(`architect`):** 확정 명세와 실제 코드를 바탕으로 구현 계획 초안·리뷰 반영 수정안을 반환한다. 구조·의존성에 영향을 주는 계획 결함도 맡되 구현자의 국소적 기술 선택을 과도하게 고정하지 않는다.
- **Planner Reviewer(`planner_reviewer`):** 명세의 사용자 흐름·관측 결과를 독립적으로 리허설하는 수용 축 리뷰어다.
- **Programmer Reviewer(`programmer_reviewer`):** 명세·계획·코드를 실제 코드베이스에 대조하는 구축 축 리뷰어다. 작성자와 별개로 지적의 해소와 검토 종료를 판단한다.
- **Implementer(`implementer`):** 검토된 계획에 따른 제품 코드·에셋·설정의 구현·수정·리팩터링·자체 확인을 맡는다. 코드 결함과 국소적 기술 선택은 직접 처리하고, 구조·의존성에 영향을 주는 계획 결함은 주 에이전트를 통해 Architect에게 반환한다. 저장 테스트는 작업별로 Implementer·Tester 중 담당을 정한다.
- **Tester(`tester`):** Implementer와 독립적으로 정해진 검증 범위와 기준에 따라 검증한다. 같은 revision에서 재현 가능한 Implementer 검사 결과(명령·종료 코드)는 재사용하고 E2E와 남은 공백을 검증한다. 완료 판정의 검증 근거는 Tester의 결과와 Tester가 확인해 재사용한 결과로 한다.
- **Art Director(`art_director`):** 사용자가 시각 검수를 요청하거나 승인된 시각적 완료 기준·아트 방향에 독립적인 판단이 필요할 때 검수·자문한다.
- **Advisor(`advisor`):** 아래 자문 조건에 해당할 때 자문한다.

작성자는 문안과 변경 요약·선택 근거·남은 판단을 반환하는 읽기 전용 역할이다. 메인은 지적별 결정과 문안의 일치를 확인해 저장하며, 작성자의 제출을 독립 검토 통과로 취급하지 않는다. 검토만 요청된 명세에 작성 단계를, 확정 명세 구현에 명세 작성 단계를 추가하지 않는다. 판정자는 같은 기준 버전·revision을 보고 첫 검토에는 상대의 결과나 작성자의 자기평가·예상 지적을 받지 않는다. 기존 판정자는 같은 세션을 이어 쓰고, 작성자에게 재요청할 때는 기준 버전·결정·미결 사항을 전달한다. 모든 역할을 항상 동시에 유지할 필요는 없다.

Jira 등록에서 요구·설계·의존 관계의 의미를 바꾸지 않는 Key·파일명·링크 치환은 등록 담당 주 에이전트가 수행할 수 있다. 이전 승인본과 새 버전의 대응·치환 내역을 기록하고 기존 등록 순서로 검증한다. 이 갱신만으로 작성자·독립 리뷰·사용자 승인을 다시 시작하지 않으며, 의미가 바뀌는 수정만 작성자와 해당 검토·승인 경로로 반환한다.

## Advisor 자문 조건

다음 경우 원래 요청·승인 범위·완료 기준, 관련 근거와 남은 판단 쟁점을 전달해 자문한다.

- 중요한 구조 결정이나, 주 에이전트가 근거로 해결하지 못한 요구·설계·범위 판단.
- 근거 있는 서로 다른 시도에도 실패 원인을 좁히지 못할 때.

새로운 판단 쟁점이나 근거가 없으면 기존 자문을 재사용하고, 추가 자문은 가능한 기존 Advisor에게 요청한다.

## 위임 경계

- 위임은 작업 단위로 묶고 필요한 맥락·승인 범위·요구 사항·완료 기준을 전달한다. 등록된 역할을 사용하며 모델·추론 수준과 역할별 수행 방법은 역할 설정을 따르고 위임 요청에서 바꾸지 않는다. 부모 모델·전체 기록을 강제 상속하는 fork 대신 새 맥락이나 필요한 일부 맥락으로 생성한다.
- 자식 에이전트의 생성·호출은 주 에이전트가 담당하며, 재위임은 주 에이전트가 명시적으로 허용한 경우에만 한다.
- 자식 에이전트는 작업 단위의 결과와 추가 판단이 필요한 쟁점을 주 에이전트에게 반환한다. Advisor 자문·사용자 질문·승인이 필요하면 필요성과 근거를 주 에이전트에게 반환한다.
- 자식 에이전트에 위임할 수 없으면 그 사실과 영향받는 작업을 사용자에게 알리고, 해당 작업을 직접 수행할지 확인을 받는다. 그와 무관한 승인 작업은 계속한다.
